# このリポジトリの作り方・実装方法のまとめ

Claude Code(AI)と一緒に、検証用のスクリプトを作って、育てていった工程の記録。**実際にやったことだけ**を書く
(2026-10-30〜31 のセッションを中心に、2026-11-05〜06 の追記を含む)。スライドや勉強会の資料の、元ネタにもなる。

> 個人を特定できる情報(ユーザー名・ホスト名)は含めない。

## 1. 全体の流れ(1つの機能が、できるまで)

```
目的を決める → 調べる(コード・ドキュメントを読む) → 小さく作る → 動かして確かめる
   → 見つかった不具合を直す → 記録する(確認できたこと/できていないこと) → PR → CI → マージ
```

例:`dep_cve_check.py`(依存関係の既知の脆弱性の確認)は、次の順で育った。

| 段階 | やったこと | きっかけ・発見 |
|---|---|---|
| 試作 | OSV に問い合わせて SARIF を出す最小のスクリプト | 「ライブラリの脆弱性を、機械的に確認したい」 |
| 実通信の検証 | PC で、古い版(`jinja2==2.10` など)を渡した | 22 件が出たが、**同じ CVE が 2 回ずつ**数えられていた |
| 直す | CVE 単位に、まとめる処理を追加 | 22 件 → 11 件 |
| 対応を広げる | NuGet、`poetry.lock`、`uv.lock`、`go.sum` | 実物のロックファイルを生成して、読み取りを確認 |
| CI に組み込む | ファイルを自動で探して照合 | 要約(`summarize.py`)にも出す |
| 突き合わせ | OSV の修正版を、GHSA と自動で比較 | 16 件中 14 件が一致(実データ) |

## 2. 確認の段階(どこで確かめるか)

環境ごとに、できることが違う。**確かめたい内容に合う場所を選ぶ**。

| 場所 | 得意 | 苦手・できない |
|---|---|---|
| クラウドのサンドボックス | コードの実装、モックでのテスト、ツールの導入(`uv`、`go`、`dotnet`)、実物のロックファイルの生成 | 外部 API への通信(許可リスト制)、LLM への通信、あなたの PC の操作 |
| あなたの PC(Windows + WSL2) | OSV・GitHub への実通信、Ollama、ポートや Windows 固有の問題 | 手作業が要る |
| GitHub Actions | インターネットに出られる、再現性がある、PR で自動実行できる | GPU が無く、LLM は小さなモデルだけ、時間がかかる |

「クラウドからは OSV に届かない → モックで検証 → PC か Actions で実通信を確認」という、**2 段構え**にした。
モックで確かめたことと、実通信で確かめたことは、ノートに**分けて書く**(「検証の状態(正直に)」の節)。

**2026-11-06追記**: 「クラウドのサンドボックス」の中身も、思っていたより広かった。
- `apt install apache2/nginx/openssh-server` で、**本物の**サーバーが動く(合成データではなく、実際のミドルウェアでの検知確認ができた)。
- `dockerd` を手動で起動すれば、Docker そのものは使える(ビルド・実行とも可能)。
- ただし、**外部への通信は、ホスト単位の許可リストで一律に決まる**。`registry.ollama.ai`・`ollama.com` は許可されておらず(403)、Docker 経由でも Ollama のモデルは取得できなかった。ここは「クラウドからは届かない」のまま変わらず、**モックの OpenAI 互換エンドポイントで配線だけ確認する**(Strix のときと同じやり方)。
- 許可リストにあるかどうかは、推測せず `curl -sS "$HTTPS_PROXY/__agentproxy/status"` で確認し、**拒否されたホストは迂回しない**(README の方針どおり、報告して終える)。

## 3. テストの方法

- **モック**: 外部通信を差し替えて、判定の分岐を確かめる。`urlopen` を差し替えた OSV・GHSA のモック、
  `mock_llm_server.py`(本物の LLM なしで、ツールの通信の仕組みを確かめる)など。
- **正解つきの的**: `vulnerable_app.py` は、11 種類の脆弱性について、脆弱版と修正版の対を持つ。
  スキャナを、「脆弱版は検出、修正版は安全」と判定できるか、数字で比べられる(検出・見逃し・誤検知)。
- **回帰テスト**: `run_regression.py` が、全 22 パターンを検証する。CI でも動かす。
- **実ログから作ったデータ**: 実際の Actions のログの内容を写した JSON を、テストデータにして、比較スクリプトを確かめた。
- **実物のファイルで確かめる**: `uv lock`、`poetry lock`、`go mod tidy`、`dotnet restore` が生成した本物のロックファイルで、
  手で作った「それらしいファイル」では見つからない問題(`[3.1.1]` の読み方など)を見つけた。
- **ばらつきを測る**: LLM の出力は毎回変わるので、同じ条件で複数回実行して、分布を見る(`aggregate_sast_runs.py`)。

## 4. スクリプトの設計の方針

- **標準ライブラリだけ**で動かす(依存を増やさない)。
- **失敗を、成功に見せない。** 接続できなかったものは、「脆弱性なし」ではなく「確認できなかった」と報告し、終了コード 2 にする。
  終了コードの意味を決めて、書いておく(0=問題なし / 1=脆弱性あり / 2=確認できなかったものがある)。
- **確認専用**: 公開 API を読み取るだけ。攻撃や悪用はしない。スキャナには、ローカルとプライベート範囲以外に撃てない仕組みを入れる。
- **共通の出力形式(SARIF)**: 出力を SARIF にそろえて、`vuln_triage.html` や `summarize.py` に、そのまま渡せるようにする。
- **既定値を変えずに、設定を足す**: ポートを環境変数(`VULN_APP_PORT`)で変えられるようにしたが、既定は、今までどおりにした。
- **他人のコードは、コミットを固定**して使う(ブランチ名ではなく SHA)。権限は読み取りだけ。実行する前に、コードを読む。

## 5. 動かして見つかった不具合(実例)

読むだけでは気づかず、**動かして、初めて見つかった**ものが多い。

| 不具合 | 見つけ方 |
|---|---|
| 同じ CVE が、GHSA と PYSEC で、2 回数えられていた | PC で実通信 |
| `.csproj` の `[3.1.1]`(固定の意味)が、範囲として飛ばされていた | `dotnet restore` の実物と比べた |
| `import os` が抜けていた(コンパイルは通る) | 実行前に、`import` を確認 |
| シェルで `$?` が、直前の `echo` の結果(常に 0)になっていた | 実データでの実行ログ |
| 比較スクリプトが、AI の「誤検知」判定を見ていなかった | AI ありのログと、表の数字の食い違い |
| `pkill -f` が、自分のシェルも止めた | 終了コード 144 |
| Windows で `printf` や `/tmp` が使えなかった | PC での実行エラー |
| ミラーモードで、Windows のサービスと、ポートが衝突した | `Address already in use` と、ポートの調査 |
| `docker run --name` で同じ名前を使い回すと、前のコンテナを消し忘れたまま、別のコンテナに置き換わっていた(モデルを取得したはずが、新しいコンテナには入っていなかった) | `docker ps -a` の「作成からの経過時間」が、想定と合わなかった |
| 旧ブランチの履歴を `git merge -s ours` で取り込んだ際、直前のコミットの変更(URL スキームの検査)が、PR の差分から消えていた | `git diff origin/main --stat` で、入っているはずのファイルの変更行数を確認 |

## 6. LLM(AI)を使うときの注意

- **出力は、実行のたびに変わる。** 同じモデル・同じコードでも、1 回目は検出 6/11、2 回目は 5/11 だった。
  1 回の結果で、優劣は決められない。複数回の分布を見る。
- **AI の「誤検知」判定を、確認せずに捨てない。** 2 回目の実行では、AI が本物の脆弱性(`/file`)を打ち消した。
- **小さなモデルは、ツールを呼べないことがある。** エージェント型のスキャナでは、7B のモデルが失敗した記録がある。
- **紹介記事の主張は、そのまま信じない。** 一次情報(リポジトリのコード、実測の記録)を読んで、確かめる。
- **2026-11-06追記(LLM を部分的に足す設計)**: 「判定(脆弱かどうか)」と「材料(ペイロード・クラスの定義)」を分けると、
  上の注意点を抑えながら LLM を足せる。
  - LLM には**材料だけ**を考えさせ、**判定は既存の決定的なルールのまま**にする(`auto_vuln_scanner.py --llm-payloads`)。
  - 判定方法自体を LLM に決めさせる場合も、**実行するコードは渡さず**、こちらで用意した小さく安全な型
    (例: 「応答にこの文字列が出たら検知」)の**パラメータだけ**を渡させる(`--llm-class`)。
    LLM の返答を `eval`/`exec` しない。JSON 以外の応答(コード実行を誘う内容を含む)は、パースに失敗して
    安全に拒否されることを、モックで確認した。

## 7. Git と PR の進め方

- **小さな PR に分ける。** 1つの PR に、無関係な変更が入ったときは、説明を実態に合わせて書き直す。
- **PR の説明に、「確認したこと」と「未確認」を分けて書く。**
- **マージ済みのブランチに、続きを積まない。** 最新の `main` から、新しく始める。
- **強制 push を使わない。** 他の PR のコミットが消えるため。載せ直して(`rebase`)から push する。
- **CI を、確認の道具に使う。** ワークフロー自身を変えた PR で、自動で一度動くようにして、マージ前に確かめる
  (`pull_request` の `paths`)。
- **結果待ちの確認を、予約する。** 長い実行(AI のスキャン)は、完了後に、ログを読んで、報告する。
- **2026-11-06追記**: squash マージされたブランチの続きをやるときは、`main` から作り直す
  (同じ名前のブランチでも、`git checkout -B <branch> origin/main`)。別の PR の変更を、通常の `push` で
  同じブランチに持っていく必要があるときは、`git merge -s ours origin/<branch>` で履歴だけ合わせられるが、
  **合わせた直後に `git diff origin/main --stat` で、入っているはずの変更が実際に残っているか確認する**
  (1 度、直前のコミットの差分が消えたまま push してしまい、気づいて復元した)。

## 8. Claude Code との進め方

1. **目的を伝える**(例:「GHSA の検証を、実通信でして」)。
2. AI が、**コードやドキュメントを読んで調べる**(推測しない)。
3. **小さく実装して、サンドボックスで動かす。**
4. **PC や Actions で、実通信を確認する。** 出力を、そのまま貼る。
5. AI が、**出力を読んで、不具合を直す。** 貼られた出力の食い違いが、手がかりになる。
6. **記録(ノート)と PR に、確認できたことと、未確認を分けて残す。**

コツ:

- エラーや出力は、**省略せずに貼る**(原因の特定が早い)。
- 「どこで、何を実行するか」(Windows か WSL か、PowerShell か)を、**コマンドごとに明記してもらう**。
  今日も、PowerShell 用のコマンドを、WSL に貼ってしまう場面があった。
- AI の説明が、**推測か、確認済みか**を聞く。「確認していない」と言わせる。

## 9. 公開するときの確認

- **ライセンス**: このリポジトリは、`LICENSE` がある。他人のコードを使うときは、ライセンスの有無を確認する
  (今回調べた `local-ai-sast` は、`LICENSE` が無かった)。
- **個人情報・秘密情報**: ユーザー名、ホスト名、API キーを、記録に残さない(伏せ字にする)。
- **攻撃系の道具の扱い**: 悪用できる内容を含めない。対象は、自分が所有するか、書面で許可を得たものだけ(`SECURITY.md`)。
- **AI が書いたコード**は、動かして確かめてから公開する。
