## TL;DR

- 攻撃用の **自律型AIエージェント**（Strix / Cairn / Hermes、そして ARTEX など）が、現実のインシデントで話題になっています。
- 私はそれを **防御側の目線**で分解し、「どこを観測すれば捕まえられるか」を **R1〜R7** という7つの検知観点にまとめ、Sigma / Falco / Elastic / Datadog のルールと小さな確認ツールにしました。
- **攻撃の手順は一切含みません**（検知・防御の設計に限定）。ツールは自分が所有／認可した対象にだけ使います。

## 背景：攻撃側が「エージェント化」している

Gambit Security のレポート（2026-09-22）は、オンライン小売を狙った攻撃で、**Strix / Cairn / Hermes** という3つのAIツールが分業して使われた事例を扱っています。ざっくり役割は次の通りです。

| ツール | 役割（防御目線の理解） |
|---|---|
| Strix | 偵察・脆弱性探索（AIペンテストツール） |
| Cairn | 探索の統括（blackboard 的な事実・意図グラフで OODA ループを回す） |
| Hermes | 汎用エージェント。**スキル**機構が拡張（＝兵器化）の入口になり得る |

その後、百度主催の攻防チャレンジで優勝したとされる **ARTEX** なども注目され、「AIが自律的に探索・実行する攻撃」はもう珍しくない前提で守る必要が出てきました。

## 発想：ツールごとに作り直さず、「観測できる挙動」で守る

攻撃ツールは増え続けますが、**観測できる挙動の土台は共通**です。

- LLM を呼ぶ（推論の通信が出る）
- 大量に探る（偵察）
- 多種のツールを短時間に連続実行する
- 任意で C2 的な外部通信や永続化をする

なので、ツール名ではなく**挙動ベース**で検知を作れば、新しいエージェントが出ても横展開できます。これを整理したのが R1〜R7 です。

## R1〜R7（検知の7観点）

| 記号 | 観点 | 一言 |
|---|---|---|
| R1 | サーバから外部 LLM API への通信 | エージェントが「頭脳」を呼ぶ動き |
| R2 | 特権 / host ネットのコンテナ起動 | 危険な足場 |
| R3 | 偵察的な Web 列挙バースト | 短時間の大量の探り |
| R4 | メッセージング API 経由の C2 的通信 | 指令チャネル |
| R5 | 永続化（cron / systemd timer）の新規作成 | 居座りの仕込み |
| R6 | 相関（上記を束ねて「連鎖」として検知） | 単発では見えないものを見る |
| R7 | 1 親プロセスが多種ツールを短時間に連続実行 | **ローカルLLM型でも残る核** |

ポイントは **R7** です。自前のローカルLLMを使うエージェントは R1（外部LLMへの通信）を避けられますが、「人間離れした速度と多様さでツールを連続実行する」挙動は残ります。

> **正直な注記**：「R1〜R7」という名前は**このリポジトリ独自の整理ラベル**で、業界標準ではありません。中身の挙動は **MITRE ATT&CK**（例：偵察 T1595、C2 T1071、永続化 T1053）に対応づけてあり、対外的に説明するときは T番号を併記するのが通じやすいです。MITRE ATLAS と OWASP Top 10 for LLM（LLM06 Excessive Agency など）への「接続点」も載せています（ID は公式で要確認としています）。

## 「検知」だけでは足りない：防御は4層

R1〜R7 は対策の全部ではなく、**検知の部分**です。対策は4層で1セットだと考えています。

1. **予防**：攻撃面を減らす（管理面を隔離、egress の allowlist、CSP、最小権限）
2. **検知**：R1〜R7
3. **応答**：見つけたら止める（遮断・隔離）
4. **復旧**：壊されても戻せる（不変バックアップ、復元テスト）

（冒頭の図が、この4層と各ツールの対応です。）

外部の導入ロードマップ案も、この4層に当てはめて評価しました（たとえば「Windows の VSS は管理者権限で消せるので真の WORM ではない」「`chmod -R 644` はディレクトリで壊れる」など、鵜呑みにすると危ない点の整理）。

## 中身：何が入っているか

| 部品 | 内容 |
|---|---|
| `security-scan/detections/` | R1〜R7 の検知ルール（**Sigma / Falco / Elastic / Datadog**） |
| `netcheck/` | 確認専用の露出チェッカー（ポート・バナー・ヘッダ・TLS・管理画面らしき URL）。**攻撃しない**。許可レンジ外は実行前に拒否 |
| `vuln_triage.html` | ブラウザ完結のトリアージ画面。Semgrep / Trivy / gitleaks / **SARIF** / netcheck の JSON を読み、優先度と直し方を出す。**外部送信なし** |
| `scripts/summarize.py` | CI のスキャン結果を要約。`--format elastic / datadog` で SIEM 向けに出力 |
| `shared/taxonomy.json` + CI | タグ・攻撃連鎖・対応スキャナ・ルール網羅表を**唯一の定義**にし、ズレを CI で検出 |
| 解析ノート | Strix / Cairn / Hermes / ARTEX の防御解析、用語集（やさしい日本語）など |

### ひとつ工夫した点：「最新化漏れ」を CI で止める

ツールを足すたびに「あっちのファイルだけ古い」が起きるのが嫌だったので、**共通定義を `shared/taxonomy.json` に一本化**し、各ツールが追従しているかを `tools/check_consistency.py`（標準ライブラリのみ）で検査して、ズレたら CI を落とすようにしました。実行時に共通ライブラリを読ませるのではなく、各ツールを自己完結（オフライン・単一ファイル）のまま保つための割り切りです。

## 試し方（自分の資産に対してだけ）

```bash
# 露出チェック（自分が管理する IP/ホストだけ。許可レンジ外は拒否されます）
python3 netcheck/netcheck.py

# 整合性チェック
python3 -I tools/check_consistency.py

# CI の結果を SIEM 形式に
python3 scripts/summarize.py results --format elastic --out scan.ndjson
```

`vuln_triage.html` はブラウザで開いて JSON をドロップするだけです。

## やっていないこと・守っている線

- **攻撃の実行手順、兵器化、安全機構の回避は作りません／載せません。** スキルの攻撃内容も転記していません。
- 攻撃ツールの解析は、公開ソースを**静的に読む**のが中心です（Hermes・ARTEX は読むだけ）。実行したのは、攻撃を伴わない検証（Strix の LLM を使わない PoC、Cairn の攻撃なし mock）だけで、実際の対象への攻撃はしていません。外部コードは信頼できない前提で扱い、サプライチェーンのリスクも注記しています。
- 運用基盤そのもの（他者が運用するインフラ）への実スキャンは、利用者であることだけでは認可されません。検証は**自分の資産／許可を得た範囲／バグバウンティのスコープ**に限ります。
- 報道ベースで未確定の話（特定インシデントとの関連など）は、**未確認として**そう書いています。

## 限界（正直に）

- 検知ルールは**単体シグナル**で、閾値・資産ゾーン・allowlist は**環境に合わせた調整が必須**です。そのまま本番に入れると誤検知が出ます。
- 検知力の本体は**相関（R6）**です。SIEM 側で時系列相関を組む前提です。
- ATLAS / OWASP-LLM との対応は「接続点」の提示で、1:1 の対応表ではありません。
- 個人の成果物なので、網羅性や保守は限られます。**フィードバック歓迎**です。

## おわりに

「攻撃側がAIでエージェント化している」こと自体は不安になりますが、**観測できる挙動は共通**で、**防御は挙動ベースで一般化できる**というのが調べて一番の収穫でした。
