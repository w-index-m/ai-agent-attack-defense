# セキュリティ問題のまとめ（日本語）

English: [`security-summary.en.md`](security-summary.en.md)

このリポジトリで扱った、AI エージェント攻撃と既知の脆弱性について、**何が起きたか・何を作ったか・何が未検証か**を1枚にまとめたもの。
個別の詳細は、各文書へのリンクを参照。

> ⚠️ 方針：このリポジトリは**検知・防御・確認**に限定する。攻撃の実行手順、兵器化、安全機構の回避方法は含まない。
> 攻撃ツールは、解析の対象であり、実際の攻撃には使っていない。実行するのは、自分が所有する・書面で許可を得た対象だけ。

---

## 1. 攻撃側の動き（調べた対象）

### 1-1. Gambit Security のレポート（2026-09-22）
オンライン小売を狙った攻撃で、3つの AI ツールが分業して使われた事例。

| ツール | 役割 |
|---|---|
| Strix | 偵察と脆弱性の探索 |
| Cairn | 探索的な侵入（目標まで自走する） |
| Hermes | 統括と事後の作業（スキルで拡張できる） |

攻撃の流れ（7段）と、対応する防御は次のとおり。詳細は [`defense-playbook.ja.md`](defense-playbook.ja.md) の §3。

| 段 | 攻撃 | 主な防御 |
|---|---|---|
| ① | ログイン画面の SQL インジェクション | パラメータ化クエリ、DB 権限の最小化 |
| ② | OTP の平文保存（MFA の回避） | ハッシュ化、短い有効期限、試行回数の制限 |
| ③ | 管理画面のアップロードに拡張子検証なし（Web シェル） | 許可リスト、実行できない保存先、Web ルートの読み取り専用化 |
| ④ | sudo のパスワードなし（権限昇格） | NOPASSWD の廃止、必要なコマンドだけの許可 |
| ⑤ | NFS の不備と、設定ファイル内の認証情報 | no_root_squash の廃止、秘密情報を設定に置かない |
| ⑥ | Secrets Manager の全件取得（IAM が広すぎる） | 最小権限、アプリごとに秘密を1つだけ許可 |
| ⑦ | カード番号の暗号鍵が同じ環境から取れる | トークン化、鍵の分離（KMS） |

### 1-2. ARTEX（自律型のペネトレーション AI エージェント）
百度の攻防チャレンジで優勝したとされる OSS。Planner と Worker の構成、記録型のプロキシ、承認ゲートを持つ。
解析は [`artex-analysis.ja.md`](artex-analysis.ja.md)。

- **韓国の金融機関の侵害との関連**は、報道のみで**未確定**。
- 「ゼロ人手で0day発見」も、中文コミュニティの転述で**未検証**。

## 2. 既知の脆弱性（別件）

### 2-1. VMware の VMSA-2026-0006
vCenter の認証不要の遠隔コード実行（最大 CVSS 9.8）を含む。**回避策は無く、パッチが唯一の対処**。
AI エージェントに限らず、このような既知の重大な脆弱性は、自動ツールに狙われやすい。
本リポジトリでは、管理面の露出確認（netcheck の 902 / 5480 / 9443）と、[`defense-detection-notes.md`](defense-detection-notes.md) の §5.1 で扱う。

## 3. 企業として取るべき対応

| 対応 | 内容 | 本リポジトリでの支援 |
|---|---|---|
| **SQL インジェクションの修正** | 該当箇所をパラメータ化クエリに直し、同じパターンを全体で探す | Semgrep（CI）、`patch_suggest.py`（修正案の diff） |
| **DB の権限** | アプリ専用アカウントに、必要な操作だけ許可する | 手作業（防御プレイブック §3 ①） |
| **機密情報の保護** | パスワードと OTP はハッシュ化、鍵は KMS などに分離 | gitleaks（CI）、防御プレイブック §3 ②⑦ |
| **露出の削減** | 管理画面、DB、ローカルの LLM API を、インターネットに直接出さない | `netcheck`、`zgrab2_guard.py` |
| **外向き通信の制限** | サーバから LLM やメッセージングへの通信を、許可リストで絞る | 検知 R1・R4 |
| **パッチ** | OS（RHEL・Windows）と製品（vCenter など）の既知の重大な脆弱性から優先する | `os_patch_check_linux.py`、`os_patch_check_windows.py` |
| **検知** | R1〜R7 のルールを、ログ基盤（SIEM）に載せる | `detections/`（Sigma・Falco・Elastic・Datadog） |

## 5. 検証の状態（正直に）

| 項目 | 状態 |
|---|---|
| ツールの構文・整合性チェック（CI） | ✅ 確認済み |
| netcheck、zgrab2 の取り込み | ✅ サンプルデータとモックで確認 |
| `patch_suggest.py` | ✅ 一時的なリポジトリとモック LLM で、生成→確認→適用を確認 |
| OS 更新の確認（RHEL・Windows） | ⚠️ 出力形式を模したスタブでのみ確認。**実機では未実行** |
| ローカル LLM への質問機能 | ⚠️ モックサーバーでのみ確認。**実機の Ollama（qwen2.5:1.5b）では未確認** |
| 検知ルールの実効性 | ⚠️ 実際の攻撃環境での検証はしていない（認可ラボが必要） |
| 攻撃ツール（Strix・Cairn・Hermes・ARTEX） | ✅ 解析のみ。実対象への攻撃は行っていない |

## 6. 限界と注意

- **小さなローカルモデル（qwen2.5:1.5b）は、誤った答えや修正を出すことがある。** 必ず人が確認すること。
- **調査は公開情報に基づく。** 攻撃側が、この順で動くとは限らない。報道による情報は、未確定として扱う。
- **このリポジトリの検知ルールは単体のシグナル。** 閾値や許可リストは、環境ごとに調整が必要。検知力の本体は相関（R6）にある。
- **自動化は段階的に。** いきなり自動で遮断すると、誤検知で自分のサービスを止める。アラートだけから始める。

## 7. 次にやること（優先順）

1. 自社のサーバで、netcheck と OS 更新の確認を実行し、結果を `vuln_triage.html` で見る
2. 見つかった SQL インジェクションを、パラメータ化クエリに直す
3. 修正後、Semgrep で同じパターンが残っていないか再確認する
4. 管理画面と DB が、インターネットから直接届いていないか確認する
5. 既知の重大な脆弱性（vCenter など）のパッチ状況を確認する
