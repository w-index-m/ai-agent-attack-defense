# AI診断(AI-SAST/AIエージェントによる脆弱性診断)の結果を人間が確認するチェックリスト

NISCの「個人情報の漏えい等につながる不正アクセスへの対策について」(2026-11-05)は、1-(3)で
「AIを活用した診断ツールの検討」を対策例に挙げつつ、「**AIによる評価結果は根拠・妥当性を確認し、
最終判断は人が行う**」と明記している(詳細: [`nisc-2026-11-05-taiou-notes.ja.md`](nisc-2026-11-05-taiou-notes.ja.md)§5-3)。
本チェックリストは、その「人が最終確認する」を具体的な運用手順に落とし込んだもの。本リポジトリの
[`ai-sast-trial-notes.md`](ai-sast-trial-notes.md)で実際に確認した、AI診断の具体的な失敗パターンに基づく。

## 0. 前提(この文書の裏付け)

`ai-sast-trial-notes.md`で、[local-ai-sast](https://github.com/sohampatil99/local-ai-sast)を
`sqli-lab/vulnerable_app.py`(正解が分かっている11種類の脆弱性)にかけて確認した事実:

- **3Bモデル、独立5回の実行で、本物の脆弱性を「誤検知」として打ち消した**: OSコマンドインジェクション
  2/5回、パストラバーサル2/5回。「誤検知として打ち消された」=そのままなら、本物の脆弱性が
  レポートから消える。
- **同じモデル・同じコードでも、実行ごとに判定が変わる**(2026-10-30の1回目と2026-10-31の2回目で、
  パストラバーサルの判定が`true_positive`→`false_positive`に反転した)。
- **モデルを大きくしても(3B→7B)、検出できる脆弱性の種類は増えなかった**(どちらもルールだけと
  同じ5/11種類)。7Bは誤検知の打ち消しが減った(本物を打ち消した回は0件)が、これも5回の結果であり
  一般化はできない。
- **残り続ける誤検知もある**: SSRFの修正版(`/fetch_url_safe`)は、3B・7Bともに複数回の実行で
  誤検知のままだった。

結論: **AIの「脆弱性なし」判定は、「本当に無い」のか「AIが見逃した・打ち消した」のかを、
AIの出力だけからは区別できない。**

## 1. レビューの手順

### 1-1. AIが「脆弱性あり」と判定したもの(true_positive / needs_review)

- [ ] 指摘されたコード箇所を実際に読み、指摘の内容(脆弱性の種類・原因)がコードと一致するか確認する。
- [ ] 一致しない場合(種類違い・場所違い)は、**指摘は無視せず**、正しい分類で別途記録する
  (`ai-sast-trial-notes.md`で確認済みの誤り: ハードコードされたパスワードの誤検知、
  `realpath`チェック済みのパストラバーサルを`true_positive`と誤判定、等)。

### 1-2. AIが「脆弱性なし / 誤検知」と判定したもの(false_positive)— 最重要

- [ ] **`false_positive`判定を無確認で握り潰さない。** ルールベース(Semgrep/Trivy等)の指摘と
  並べて確認し、ルールベース側で指摘があるのにAIが打ち消している場合は、必ず人間がコードを読んで
  裏取りする。
- [ ] 同じ対象に対する過去の実行結果があれば、**今回の判定と食い違っていないか**を確認する
  (食い違いがあれば、どちらか一方が誤り。放置しない)。
- [ ] 入力検証・エスケープ・パラメータ化が実際にされているか、コードを目で追って確認する
  (AIの「されているはず」という判断を信用しない)。

### 1-3. 複数回実行した場合

- [ ] 1回の結果だけで「安全」と判断しない。最低でも数回は実行し、判定が割れていないか確認する。
- [ ] 判定が割れた場合、**より厳しい方(脆弱性ありとする方)を採用する**(安全側に倒す)。

### 1-4. 承認

- [ ] 「AIが安全と言った」ことを、リリース判断・修正不要の根拠として**単独では使わない**。
  最終承認は人間が行う(NISCの要請、本リポジトリの`agent_tool_guard.py`が採る「迷う場合は拒否側に
  倒す」という方針とも一致する)。
- [ ] レビュー結果(一致/不一致・最終判断・根拠)を記録に残す(どのツールでレビューしたかは問わない。
  本チェックリストのコピーに書き込む、Issue・チケットに残す、等)。

## 2. 既知の誤判定パターン(本リポジトリで実際に確認済み。新しいモデル・対象でも疑うべき箇所)

| パターン | 内容 | 出典 |
|---|---|---|
| 本物の脆弱性を誤検知として打ち消す | OSコマンドインジェクション・パストラバーサルで発生(3Bモデル) | `ai-sast-trial-notes.md`§7Bのモデルでの実験 |
| 同じ入力で判定が反転する | 同じモデル・同じコードで、2回の実行間でパストラバーサルの判定が逆転 | `ai-sast-trial-notes.md`2026-10-31の実行 |
| 誤った種類で`true_positive`判定 | ハードコードされたパスワード扱いの誤り、`realpath`チェック済みの箇所を脆弱と誤判定 | `ai-sast-trial-notes.md`2026-10-30の実行 |
| 検出範囲がモデルサイズで広がらない | 3B→7Bにしても、検出できる脆弱性の種類数は変わらなかった(反射型XSS・格納型XSS・CSRF・IDOR・マスアサインメント・アカウント列挙は両方で見逃し) | `ai-sast-trial-notes.md`§7Bのモデルでの実験 |
| 同じ誤検知が繰り返し残る | SSRFの修正版が、複数回・複数モデルで誤検知のまま | `ai-sast-trial-notes.md`全体 |

## 3. 適用範囲

本チェックリストは、AI-SASTツール(コードを読んで脆弱性を指摘するAI)を想定して書いたが、
考え方は`auto_vuln_scanner.py`の`--llm-payloads`/`--llm-class`(LLMが追加ペイロード・新クラスの
判定方法を提案する機能)にも同様に当てはまる。両方とも、本リポジトリの方針は**「LLMの判定を
そのまま信じない」**で一貫している(`sqli-lab/README.ja.md`の`LLM_CAUTION_NOTE`参照)。
