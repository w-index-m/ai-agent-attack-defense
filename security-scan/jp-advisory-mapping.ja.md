# 国内の注意喚起と、このリポジトリの対応表

English: [`jp-advisory-mapping.en.md`](jp-advisory-mapping.en.md)

2026年10月7〜9日に、個人情報保護委員会、JPCERT/CC、国家サイバー統括室、IPA などが、国内組織で相次ぐ不正アクセスによる個人情報の漏えいを受けた注意喚起を公表した。
その内容を、このリポジトリの防御と照らし合わせた 1 枚。**防御の整理に限定し、攻撃の手順は書かない。**

> ⚠️ 出典の扱い：
> - **§1〜§3（4 つのケースと対応表）**は、ブログ（piyolog、2026-10-11）の要約を、ユーザーが画像で共有したものに基づく**二次情報**。
> - **§4（JPCERT/CC の推奨する対策）**は、JPCERT/CC の注意喚起（2026-10-08 公開、2026-10-09 に「I. 概要」「II. 確認されている攻撃手法や攻撃の痕跡」を追記）の「対策」「参考情報」の節を、ユーザーが貼り付けた**原文**に基づく。
> - 正確な内容と最新の情報は、JPCERT/CC の注意喚起と個人情報保護委員会（10月7日改訂の WARNING）の原典で確認すること。CVE 番号も、原典で確認すること。
> また、注意喚起自体が「すべての事案で同一の手法が使われているわけではない」とし、「把握している情報は限定的かつ断片的」としている。

## 1. 注意喚起の 4 つの型と、個人情報保護委員会の事例

JPCERT/CC が示した 4 つのケース（高い粒度のみ）。

| ケース | 内容 |
|---|---|
| A | 標的ごとに既知の脆弱性の有無を探して悪用を試みる。脆弱性ではなく、機器の管理不備（設定ファイルやバックアップの取得など）も狙われうる |
| B | API 経由の不正な操作。公開アプリの解析から API の情報を知る、画面からは実行できない内部 API を狙う、他システムで盗んだ API キーを使う |
| C | Metabase の SQL インジェクションの脆弱性（記事では CVE-2026-72898、ゼロデイ攻撃が確認されたとされる）。API への不正なリクエストで悪用 |
| D | 公開 Web サーバーから届くアプリケーションサーバー上に、WAR ファイルが設置された事案（JSP が簡易 Web シェルとして動作）。10月9日に追加 |

個人情報保護委員会（10月7日改訂の WARNING）は、漏えい事案を 9 つの事例に分類した。その事例 9 は「API が悪用される事例」で、API の設計・設定の不備により、ログイン後のパラメータの書き換えで、他の利用者の情報が取れる状態だった。

## 2. 対応表

「このリポジトリ」の列は、文書とツールの現状（確認日：2026-10-11）。**実機での検証はしていない。**

| 型 | 防御（予防） | 検知 | このリポジトリの状態 | 足りない点 |
|---|---|---|---|---|
| A 既知の脆弱性の探索 | パッチの優先適用、公開範囲の縮小 | 外部からの列挙（R3） | OS 更新の確認（`os_patch_check_*`）、Trivy、netcheck、R3 | 製品ごとの悪用の検知 |
| A 管理不備（設定・バックアップ） | Web から取れる場所に置かない | Web ルート配下のファイルへのアクセス | プレイブック §3A-D に項目を追加。**netcheck が 15 件の露出を確認**（`.env`、`.git`、DB のダンプ、バックアップなど。実機では未検証） | ファイルへのアクセスの検知は無い |
| B API の不正操作（認可の不備） | サーバ側で、利用者ごとに認可を確認する | API ログの異常（大量呼び出し、401/403 の急増） | プレイブック §3A-A に項目を追加 | **検知ルールが無い**。API の認可を点検する道具も無い |
| B API キーの悪用 | キーの権限の絞り込みと定期的な作り直し | キーの使用の異常 | gitleaks、プレイブック §3A-B | キーの使用の検知、罠（§5 は設計のみ） |
| C BI ツールの脆弱性 | 公開しない（VPN・IP 制限）、パッチ | 管理系ポートへの外部アクセス（R3） | netcheck、プレイブック §3A-C | 製品固有の検知。**Metabase を名指しした項目は無い** |
| D Web シェルの設置 | アップロードの許可リスト、実行権限なし、Web ルートの読み取り専用 | Web ルートへの新規ファイル、Web サーバ配下からの子プロセス | プレイブック §3 ③、**R8**（Sigma / Falco の 2 ルール：設置と、Web サーバーからのシェル起動） | Elastic / Datadog 版は未実装。実環境での検証は未実施。FIM の本格運用は別 |
| 事例 9 API の悪用 | 型 B と同じ | 型 B と同じ | プレイブック §3A-A | 同上 |

## 3. 見えてきた課題（優先順）

1. **API の認可の点検と検知。** 型 B と事例 9 は、このリポジトリでいちばん手薄。まず、API ごとの認可の確認を、運用の手順に入れる。
2. **設定・バックアップの露出の確認。** `netcheck` に実装済み（15 件）。実機での検証が次の課題。
3. **Web シェルの設置の検知。** R8 を Sigma / Falco に実装済み。Elastic / Datadog 版と、実環境での調整・検証が残っている。
4. **BI ツールなど、製品固有の悪用への備え。** 公開範囲の縮小とパッチの優先が基本。

## 4. JPCERT/CC が推奨する対策と、このリポジトリの対応

JPCERT/CC は、報告されている手口に基づく対策として、次を推奨している（要旨。原文は注意喚起を参照）。API 経由のアクセスへの対策の詳細は、OWASP のガイドラインなどを参考にするとされている。

**API 経由のアクセスへの対策**

| 推奨 | このリポジトリの状態 |
|---|---|
| API へのアクセスに、単位時間あたりの件数の制限を設け、短時間の繰り返しや大量の実行を防ぐ | プレイブック §3A-A に追記（レート制限）。実装・検知は無い |
| ログイン、パスワードリセット、SMS 送信、検索など、負荷や悪用のリスクが高い機能に、個別のレート制限や回数制限を設ける | 同上 |
| 非公開 API を含む各エンドポイントで、アクセス制御を行い、許可された利用者と HTTP メソッドだけを受け付ける | §3A-A（認可）に追記 |
| API の利用者とトークンに、必要最小限の権限だけを与える | §3A-B に追記 |
| トークンに適切な有効期限を付け、長期間有効なものを避ける | §3A-B に追記 |
| 不要になった、または漏えいが疑われるトークンを、速やかに無効化できるようにする | §3A-B に追記（応答） |

**汎用的な対策**

| 推奨 | このリポジトリの状態 |
|---|---|
| 利用地域が限定されるサービスは、アクセス元の地域を制限する | §3A-E に追記 |
| 既知の脆弱性の影響を受けるバージョンは、修正済みの更新を適用する | OS 更新の確認、Trivy、プレイブック §3A-C |
| Web サーバーなどが侵害された後の、横展開への対策を見直す | 7 段の ④⑤⑥（§3）と §3A-E |
| 不正アクセスの検知体制と、検知時の初動対応を見直す | 検知ルール R1〜R7（ネットワーク・ホスト）、プレイブック §4。API ログの検知は無い |
| 漏えいを想定し、平時から顧客に二次被害防止を呼びかける（多要素認証など） | §3A-E に追記 |
| 業務上不要なサービスや機能（管理機能など）が公開されていれば、公開を止める | netcheck、プレイブック §3A-C |
| 保存期間を過ぎたデータや、利用目的を終えたデータを残さない | §3A-E に追記 |

JPCERT/CC は、不特定多数の利用を想定していないシステム（従業員向け、BI ツールなど）も被害に遭っているので、同様の点検を推奨している。
