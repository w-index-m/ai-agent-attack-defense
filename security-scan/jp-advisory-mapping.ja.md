## 1. 注意喚起の 4 つの型と、個人情報保護委員会の事例

**概要（原文の要旨）**：2026年9月前後に、国内組織で不正アクセスによる個人情報等の漏えいが相次いでいる。複数の製品やサービスで被害が出ている。ランサムウェアなどとは別の、大量の個人情報の漏えいにつながる攻撃類型を取り上げている。**一般利用者向けのアプリのほか、BI ツールや従業員向けの管理システムなど、不特定多数の利用者からのアクセスを想定していないシステムも被害に遭っている。**

JPCERT/CC が示した 4 つのケース（高い粒度のみ）。

| ケース | 内容（原文に基づく） |
|---|---|
| A | さまざまなソフトウェアの**既知の脆弱性を、標的ごとにスキャン**して悪用を試みる。脆弱性ではない、機器の管理不備（**環境設定ファイルやバックアップファイルの窃取**など）の悪用も試みている可能性がある。10月9日に、不審な送信元 IP アドレスが追加された |
| B | **API 経由の不正な操作**。アプリの管理用 API への不正なリクエストで、情報の書き換えなどが起きている。手口の報告は、(a) 公開のスマートフォンアプリを解析して API の情報を特定する、(b) 画面からは実行できない内部 API を狙う（権限の変更、不正なアカウントの作成、認証の応答の違いの確認、NoSQL インジェクションによるアカウント情報の特定）、(c) 他のシステムの侵害で盗んだ API キーを使う。10月9日に、不審な送信元 IP アドレスが追加された |
| C | **Metabase の SQL インジェクションの脆弱性（CVE-2026-72898）**。認証なしで細工したリクエストを送ると、アプリケーションデータベースに不正な SQL が実行され、管理者権限を取られうる。API への不正なリクエストで悪用される。**Metabase によると、ゼロデイ攻撃が確認されている**（JPCERT-AT-2026-0023）。悪用は 8月上旬から 9月上旬の間とされる。Metabase は同日に、**別の** SQL インジェクション（CVE-2026-72899、公開共有ダッシュボード経由。GHSA-r8h2-qpfx-mx59）も公表している（§4.1） |
| D | **公開 Web サーバーからアクセスできるアプリケーションサーバー上に、WAR ファイルが設置された**事案（10月9日に追加）。WAR に含まれる JSP が、悪性の簡易 Web シェルとして動作する。特定のクエリパラメーターを取得し、シェルコマンドとして実行する機能を持つ。9月ごろ、Web シェルへの GET と POST の繰り返しのアクセスが確認されている |

原文には、ケースごとの**不審な送信元 IP アドレスと User-Agent の例**が載っている。IP アドレスは、悪用された時期が限られ、正規の利用だった可能性もあるとされている。このリポジトリには**転記しない**（古くなる、誤検知につながる）。侵害の調査には、原文のものを使うこと（§5）。

ゼロデイ攻撃の確認は、JPCERT-AT-2026-0030 ではなく、**JPCERT-AT-2026-0023**（Metabase の情報として）に記載されている。ブログ（二次情報）の「ゼロデイ攻撃が確認された」は、この点で正しかった。

個人情報保護委員会（10月7日改訂の WARNING）は、漏えい事案を 9 つの事例に分類した。その事例 9 は「API が悪用される事例」で、API の設計・設定の不備により、ログイン後のパラメータの書き換えで、他の利用者の情報が取れる状態だった。

## 3. 見えてきた課題（優先順）

1. **API の認可の点検と検知。** 型 B と事例 9 は、このリポジトリでいちばん手薄。まず、API ごとの認可の確認を、運用の手順に入れる。
2. **設定・バックアップの露出の確認。** `netcheck` に実装済み（15 件）。実機での検証が次の課題。
3. **Web シェルの設置の検知。** R8 を Sigma / Falco に実装済み。Elastic / Datadog 版と、実環境での調整・検証が残っている。
4. **BI ツールなど、製品固有の悪用への備え。** ケース C の CVE-2026-72898 と CVE-2026-72899 は**別の脆弱性**（Metabase が同日に公表）。両方の修正を含む版に上げているかを確認する。 公開範囲の縮小とパッチの優先が基本。ケース C は、アプリのパッチ適用の確認が必要（`os_patch_check_*` は OS のみで、Metabase のようなアプリは対象外）。

## 4. JPCERT/CC が推奨する対策と、このリポジトリの対応

JPCERT/CC は、報告されている手口に基づく対策として、次を推奨している（要旨。原文は注意喚起を参照）。API 経由のアクセスへの対策の詳細は、OWASP のガイドラインなどを参考にするとされている。

**API 経由のアクセスへの対策**

| 推奨 | このリポジトリの状態 |
|---|---|
| API へのアクセスに、単位時間あたりの件数の制限を設け、短時間の繰り返しや大量の実行を防ぐ | プレイブック §3A-A に追記（レート制限）。実装・検知は無い |
| ログイン、パスワードリセット、SMS 送信、検索など、負荷や悪用のリスクが高い機能に、個別のレート制限や回数制限を設ける | 同上 |
| 非公開 API を含む各エンドポイントで、アクセス制御を行い、許可された利用者と HTTP メソッドだけを受け付ける | §3A-A（認可）に追記 |
| API の利用者とトークンに、必要最小限の権限だけを与える | §3A-B に追記 |
| トークンに適切な有効期限を付け、長期間有効なものを避ける | §3A-B に追記 |
| 不要になった、または漏えいが疑われるトークンを、速やかに無効化できるようにする | §3A-B に追記（応答） |

**汎用的な対策**

| 推奨 | このリポジトリの状態 |
|---|---|
| 利用地域が限定されるサービスは、アクセス元の地域を制限する | §3A-E に追記 |
| 既知の脆弱性の影響を受けるバージョンは、修正済みの更新を適用する | OS 更新の確認、Trivy、プレイブック §3A-C |
| Web サーバーなどが侵害された後の、横展開への対策を見直す | 7 段の ④⑤⑥（§3）と §3A-E |
| 不正アクセスの検知体制と、検知時の初動対応を見直す | 検知ルール R1〜R8（ネットワーク・ホスト）、プレイブック §4。API ログの検知は無い |
| 漏えいを想定し、平時から顧客に二次被害防止を呼びかける（多要素認証など） | §3A-E に追記 |
| 業務上不要なサービスや機能（管理機能など）が公開されていれば、公開を止める | netcheck、プレイブック §3A-C |
| 保存期間を過ぎたデータや、利用目的を終えたデータを残さない | §3A-E に追記 |

JPCERT/CC は、不特定多数の利用を想定していないシステム（従業員向け、BI ツールなど）も被害に遭っているので、同様の点検を推奨している。

### 4.1 ケース C（Metabase）：JPCERT-AT-2026-0023 の要旨（原文で確認済み）

- **内容**：Metabase は 2026-08-06（日本時間）に、SQL インジェクション（CVE-2026-72898）を公表した。認証なしで細工したリクエストを送ると、アプリケーションデータベースに不正な SQL が実行され、Metabase の管理者権限を取られうる。
- **悪用**：Metabase によると、ゼロデイ攻撃が確認されている。海外の複数の組織が被害を公表し、8月2日に悪用されていたとの情報もある。PoC とみられる情報もあり、攻撃が広がるおそれがある。
- **対象**：63 系は x.63.5、62 系は x.62.9、61 系は x.61.11、60 系は x.60.17、59 系は x.59.21、58 系は x.58.24 より前。58 系より前は影響を受けない。Metabase Cloud は対策済み。
- **対策**：最新版へ更新する。
- **回避策**：すぐに更新できない間は、ネットワーク機器などで、`/api/session/reset_password` へのアクセスを遮断する。
- **侵害調査**：このエンドポイントがインターネットから届く状態だった場合は、更新だけで終わらせず、侵害の有無を確認する。Metabase やネットワーク機器のログで、`POST /api/session/reset_password`（HTTP 400）に続いて `GET /api/user/current`（HTTP 200）が続いていれば、侵害されている可能性が高いとされる。可能性がある場合は、ユーザーセッション、API キー、管理者アカウントを確認し、接続先データベースの認証情報を変更し、ログを確認する。
- **Metabase 自身のアドバイザリ（GHSA-vwf4-m7j8-wcjf）の原文（ユーザーが貼り付け）で確認済み**：Critical。ベンダーは**実際の悪用を確認**したと明記。回避策（`/api/session/reset_password` の遮断）と、更新後の対応（`core_session` の全行の削除、API キー・管理者アカウントの確認、接続先データベースの認証情報の入れ替え、ログの確認）、修正済みの版（58.24 / 59.21 / 60.17 / 61.11 / 62.9 / 63.5）は、JPCERT/CC の原文と一致する。CVSS 10.0 は要約による。**ログのパターン（POST 400 → GET 200）は、このアドバイザリの原文には無い**。JPCERT/CC が Metabase の情報として示したもので、出典は Metabase の告知の可能性があるが、未確認。
- **別の脆弱性（CVE-2026-72899、GHSA-r8h2-qpfx-mx59）の原文（ユーザーが貼り付け）で確認済み**：Metabase は同日に公表した。公開共有のカードやダッシュボードのうち、フィールドフィルターのパラメータを公開しているものを通じて、認証なしで SQL を実行され、管理者権限を取られうる（公開共有は既定で有効）。影響を受ける版と修正版は、72898 と同じ系列の版（x.58.24 / 59.21 / 60.17 / 61.11 / 62.9 / 63.5）。暫定対策は、公開共有の無効化、または該当する公開リンクの非公開化。**原文には、悪用の確認の記載は無い**。JPCERT/CC は、この脆弱性の PoC とみられる情報も公開されていることを確認している。

**影響の規模（Wiz Research の記事、2026-08-10、要約）**：Metabase Cloud への実際の悪用（ゼロデイ）として 2026-08-06 に開示され、Framework・Tally・n8n・Kilo Code（Anaconda）・ChecklyHQ など、影響を受けた企業が 8月7〜10日に順次公表した。Wiz の観測では、クラウド環境の約 13% が自前ホストの Metabase を持ち、そのうち約 25% がインターネットから直接届く状態。Shodan には約 2,500 件が見つかる。8月10日正午(UTC)時点で、公開の PoC がオープンソース化された。**この記事には、脆弱性の再現手順（デコンパイル結果、リクエストの組み立て方）が含まれるが、このリポジトリには取り込まない**（攻撃の再現手順は含めない方針のため）。露出を減らす対策（netcheck の活用）の裏付けとして、規模の事実のみを記載する。
- ケース C の注意喚起 0030 に出てくる User-Agent の例 `Metabase-GHSA-vwf4/2.0` は、CVE-2026-72898 のアドバイザリ（GHSA-vwf4-m7j8-wcjf）の ID と対応している。

## 5. 侵害の調査（インジケーター）

JPCERT/CC は、「侵害調査にご活用ください」として、原文に**不審な送信元 IP アドレス**（ケースごと）と **User-Agent の例**（ケース B・C）を載せている。

- 自分の環境のアクセスログ（Web サーバー、API、プロキシ、BI ツールなど）で、**原文の IP アドレスと User-Agent を検索する**。IP アドレスには、悪用された時期（8月上旬〜10月上旬）が注記されているので、**その時期のログ**を見る。
- IP アドレスが一致しても、**正規の利用だった可能性**がある（原文に注記がある）。一致しないことは、侵害が無いことの証明にならない。
- User-Agent（`curl/…`、`python-requests/…`、一般的なブラウザ）は、**単独では弱いシグナル**。自動化されたクライアントを示すにとどまり、検知の根拠にしてはいけない。
- ケース C（Metabase）は、Metabase やネットワーク機器のログで、**`POST /api/session/reset_password`（400）に続く `GET /api/user/current`（200）**の並びを探す（§4.1）。これは Metabase が示した侵害の兆候で、**1 件だけでは判断せず、続けて起きているかを見る**。
- ケース D は、公開 Web サーバーの先にあるアプリケーションサーバーの、**`.war` と `.jsp` の設置**と、その配下から**シェルが起動された形跡**を確認する（検知は R8）。

## 5A. 民間の分析：Macnica（統計・傾向）と Scutum（AI エージェントの技術的確認）

> この節は、JPCERT/CC や個人情報保護委員会の公式発表ではなく、**民間企業の技術ブログ**に基づく。ユーザーが貼り付けた原文で確認済み。

### Macnica セキュリティ研究センター（瀬治山豊氏、2026-10-07 公開、10-08 追記）

- **件数の推移**：この種の被害公表は、2024年62件→2025年84件→2026年は10月6日時点で119件（合計265件）。**今年公表された119件のうち約68%（81件）が7月以降**に集中。
- **狙われるサイトの変化**：従来は EC サイトのカード情報が中心だったが、現在は図書館の蔵書検索、観光列車の座席予約、大学施設予約など、**多種多様なサイトが無差別に狙われている**。
- **攻撃手法の内訳**（7月以降の81事案）：①共通ソフトウェアの脆弱性 9件、②認証情報の悪用 4件、③サイトの設定・アクセス制御の不備 3件、**④原因の説明が不足しているもの 65件（80.2%）**。原因を特定できる公表は少ない。
- **対応事案（ログ分析）から見えた実態**：特定の脆弱性だけでなく、**サイト全体を広く調べ、画面や API を通常どおり動かしながら不備を探す動き**。スマホアプリを解析して API キーを取り出すケースも。偵察と攻撃が明確に分かれていないこともある。
- **AI の関与について（この記事の時点）**：「**ゼロデイ脆弱性の悪用は確認されていない**」「AI の活用は、調査の広さ・速さから**否定する方が難しい**が、**断定はできない**」としている。この点は、§5A の Scutum の記事（後述）で状況が変わる。
- **海外の状況**：2026年7〜9月に13カ国・地域で計99件を確認。韓国30件、フランス11件、ポーランド8件。

### Scutum（セキュアスカイ・テクノロジー / ビットフォレスト、金床氏、2026-10-14 公開）

- **AI エージェントの関与を、技術的に確認したと明言**。WAF 側に、攻撃元が AI エージェントかどうかを判定する仕組みを独自に実装し、2026年10月10日夜から監視。**10月14日までに、少なくとも3つの IP アドレスから、AI エージェントによる日本企業のサイトへの攻撃を確認**。
- **判定手法の詳細は、対策を回避されるため非公開。** 性質として「漏れなく列挙はできないが、検知した場合は AI エージェントであるとほぼ断定できる（false positive はほぼ無いが、false negative はありうる）」としている。試した8種類の高性能モデルすべてで検出できたとも述べている（この主張自体は検証できていない）。
- **観測された攻撃パターン（要旨、IP アドレスはこのリポジトリには転記しない。原文を参照）**：
  - 1つの IP は、単純な大量スキャンのみ（古典的な挙動）。
  - 別の1つの IP は、**偵察→管理画面・バックアップファイルの網羅スキャン→SQL インジェクションの試行→問い合わせフォームへの自動投稿**と、約2時間強かけて**段階的にツールと手口が切り替わる**、教科書的な動き。
  - もう1つの IP は、約8時間にわたり、**低速スキャン→高速スキャン→既知の脆弱性への攻撃→Nmap→ログイン総当り→別の既知の脆弱性への攻撃**と、**多数のツール・手口を長時間かけて使い分ける**動き。
  - **このリポジトリの R7（1 親プロセスが多種のセキュリティツールを短時間に連続実行）が想定する挙動と、方向性が一致する**（ここでは「短時間」ではなく、数十分〜数時間という幅はあるが、「段階ごとに異なるツール・手口へ切り替わる」という核は同じ）。スキャン対象には `.git`・`.env`・`backup.zip`・`db_backup.sql` など、`netcheck` の §3A-D で確認する項目と重なるものが含まれる。
  - **A2B 攻撃で見られるような「User-Agent にスマホアプリの文字列」は、この3件では見られなかった**としている。
- **対策の結論**：AI エージェントの有無によらず、**対策の本質は変わらない**（脆弱性を無くす、シグネチャだけに頼らない WAF を使う）としている。

### このリポジトリとの接続

| 気づき | 対応 |
|---|---|
| 段階ごとにツール・手口が切り替わる、時間の長い攻撃パターン | R7 の実例として参考になる。ただし「短時間」の閾値は、この事例（数十分〜数時間）に合わせて緩めることを検討する価値がある |
| `.git`・`.env`・バックアップファイルのスキャン | `netcheck` の §3A-D（設定・バックアップの露出確認）で、同じ種類のファイルを確認できる |

| AI 関与の判定手法そのもの | Scutum は非公開としている。再現・検証はできない |
