# sqli-lab 検証まとめ(2026-10-25)

English: [`verification-log.en.md`](verification-log.en.md)

`security-scan/sqli-lab/`(意図的に脆弱なFlaskデモアプリ)に対して行った、2つの作業の
まとめ。

1. ユーザー自身のWSL環境向けの機能追加(`VULN_APP_HOST`、リポジトリにマージ済み)
2. このセッションのサンドボックス環境での、全9脆弱性クラスの実機検証(リポジトリへの
   変更は無し、検証記録のみ)

## 1. 機能追加: `VULN_APP_HOST`環境変数(マージ済み、PR #65)

### 課題

WSL環境で`vulnerable_app.py`を特定のIPアドレス(例: WSLのeth0アドレス)宛に待受させる
には、毎回`sed`でソースコードを書き換える必要があった:
```bash
sed -i 's/host="127.0.0.1", port=5000/host="0.0.0.0", port=5000/' vulnerable_app.py
```

### 変更内容

`vulnerable_app.py`のメインアプリの待受アドレスを、環境変数`VULN_APP_HOST`から読み込む
ように変更(既定値は従来どおり`127.0.0.1`):
```python
bind_host = os.environ.get("VULN_APP_HOST", "127.0.0.1")
app.run(host=bind_host, port=5000)
```

SSRFデモ用の内部限定サービス(ポート5001)は、「外部から直接届いてはいけない」という
デモの前提そのものなので、意図的に`127.0.0.1`固定のまま変更していない。

### 使い方

```bash
python3 vulnerable_app.py                              # 既定: 127.0.0.1のみ
VULN_APP_HOST=172.25.212.244 python3 vulnerable_app.py  # そのIPで待受(sed不要)
```

## 2. 全9脆弱性クラスの実機検証(サンドボックス環境、記録のみ)

`security-scan/sqli-lab/`が再現する脆弱性クラスを、1つずつ脆弱版/修正版のペアで実際に
攻撃し、挙動の違いを確認した。詳細なスクリプト側ログ・サーバー側ログ・SQLの実行過程は
別途お渡し済みの詳細レポートを参照。ここでは結果の要点のみまとめる。

| # | クラス | 検証内容 | 結果 |
|---|---|---|---|
| 1 | **sqli**(SQLインジェクション) | `username=admin' --`でパスワード条件をコメントアウト | **成立。** パスワード無しでadmin(is_admin=1)としてログイン成功。実在の`/tmp/sqli_lab.db`(SQLite)を直接確認し、本物のSQLエンジンが動いていることも裏取り |
| 2 | **cmdi**(OSコマンドインジェクション) | `host=x; id`等のシェルメタ文字 | **成立。** `id`コマンドの出力がレスポンスに漏洩 |
| 3 | **ssrf**(サーバーサイドリクエストフォージェリ) | `/fetch_url`経由で内部限定サービス(ポート5001)にアクセス | **成立。** `INTERNAL-SECRET-KEY-DO-NOT-EXPOSE`を外部から取得 |
| 4 | **traversal**(パストラバーサル) | `../../../../etc/passwd` | **成立。** `/etc/passwd`の中身がそのまま返った |
| 5 | **xss**(反射型XSS) | `<script>alert(1)</script>` | **成立。** タグがエスケープされずそのまま出力 |
| 6 | **stored_xss**(格納型XSS) | コメント投稿にスクリプトを混入 | **成立。** 投稿後、閲覧者全員に影響する永続的なXSS |
| 7 | **mass_assignment** | サインアップ時に`is_admin=true`を混入 | **成立。** 指定した権限フラグがそのまま採用 |
| 8 | **idor**(IDOR/BOLA) | aliceとしてログインしたまま`user_id=3`(admin)を指定 | **成立。** adminのプライベートノート(復旧コード)まで取得 |
| 9 | **account_enum**(アカウント列挙) | 登録済み/未登録メールでレスポンスを比較 | **成立。** レスポンスの差分でメールアドレスの登録有無が判別可能 |
| 10 | **deserialize**(安全でないデシリアライズ→RCE) | 細工したpickleペイロードで`os.system()`を実行 | **成立(最もインパクト大)。** 実際にOSコマンドが実行され、`uid=0(root)...`の出力をファイルに書き込ませることに成功(サンドボックスのプロセスがroot権限だったため) |
| 11 | **csrf** | 実際のブラウザ(Playwright/Chromium)で、別オリジンの罠ページから自動送信フォームを実行 | **成立。** 被害者が罠ページを開いただけで、残高が100→50に減少。修正版はCSRFトークン不一致で403拒否 |

全クラスで、修正版エンドポイント(`_safe`サフィックス)は同一ペイロードに対して正しく
拒否/無害化することも確認した。

### 技術的に興味深かった2点

1. **本物のSQLを使っているのは`sqli`クラスだけ**。他の10クラスはメモリ上の
   辞書/リスト/setで再現されており、SQLインジェクションとは別種の脆弱性(認可漏れ、
   エスケープ漏れ等)であることが、データストアの違いからも裏付けられる。

2. **`SameSite=Lax`だけではCSRFを防げない**。セッションCookieには`SameSite=Lax`が
   設定されていたが、罠ページの`<form method="POST">`による自動送信(トップレベル
   ナビゲーション扱い)は`Lax`でも通ってしまい、攻撃は成立した。`Strict`への変更は
   正規の遷移にも影響しうるため、**CSRFトークンのような明示的な対策が必要**、という
   実務上の教訓を実機で確認できた。

## 補足

- 今回の検証はすべて、このセッションのクラウドサンドボックス環境内(ユーザーのWSL環境
  とは別)で、`127.0.0.1`上でのみ実施した。
- リポジトリへのコード変更は(`VULN_APP_HOST`機能追加を除き)無し。検証自体は確認・記録
  目的に限定し、攻撃手順の一般化や自動化ツール化は行っていない。
