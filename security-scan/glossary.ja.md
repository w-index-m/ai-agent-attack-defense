# 用語集（やさしい日本語）

このリポジトリや会話で出てくるセキュリティ用語を、**できるだけやさしい日本語**でまとめたもの。
正確さより「まず意味をつかむ」ことを優先しています。詳しくは各ノートを参照。

関連: [`defense-detection-notes.md`](defense-detection-notes.md) / [`defense-layers-and-roadmap.md`](defense-layers-and-roadmap.md)

---

## 防御の考え方・4層

| 用語 | やさしい説明 |
|---|---|
| 予防（prevent） | そもそも攻撃を成立させないこと。攻撃できる入口（攻撃面）を減らす・塞ぐ。本リポの記号は **③**。 |
| 検知（detect） | 攻撃が起きたことを見つけること。本リポの記号は **R1–R7**。 |
| 応答（respond） | 見つけたら止める・封じ込めること（遮断・隔離）。 |
| 復旧（recover） | 壊されても元に戻せること（バックアップ・復元）。 |
| 攻撃面（attack surface） | 攻撃者が狙える入口の広さ。公開ポート・管理画面・古い部品などが増えると広がる。 |
| 堅牢化（hardening） | 初期設定のまま使わず、不要な機能を切る・権限を絞るなどで固めること。 |
| プレイブック | 「こういう状況では、誰が何をするか」を手順にまとめたもの。本リポの [`defense-playbook.ja.md`](defense-playbook.ja.md) は、攻撃連鎖の段ごとの防御と対応の手順。 |
| ハニートークン（罠） | 本物の業務では使われない偽の認証情報や偽のデータ。使われたら不正の可能性が高いので、誤検知の少ない警報になる。予防ではなく検知の補助。 |
| 机上訓練（tabletop） | 実際には何も動かさず、シナリオを順にたどって「ここで気づけるか、誰が何をするか」を確認する訓練。 |
| ローテーション（鍵・認証情報の更新） | 鍵や認証情報を新しいものに作り替え、古いものを無効にすること。漏れた可能性があるときの基本の対応。 |
| 多層防御（defense in depth） | 1つの対策に頼らず、予防・検知・応答・復旧を重ねること。 |
| allowlist / denylist | 許可リスト／拒否リスト。「許可したものだけ通す」allowlist の方が安全。 |
| 最小権限（least privilege） | 必要な分だけ権限を与える考え方。1つ破られても被害を小さくできる。 |

## 本リポジトリの記号

| 記号 | 意味 |
|---|---|
| R1 | サーバから外部の **LLM** への通信（AIエージェントが頭脳を呼ぶ動き） |
| R2 | **特権コンテナ**の起動（権限の強いコンテナ＝危険な足場） |
| R3 | **偵察**の列挙バースト（短時間に大量の探り） |
| R4 | メッセージングでの **C2** 通信（指令チャネル） |
| R5 | **永続化**の新規作成（再起動後も残る仕込み） |
| R6 | **相関**（R1〜R5・R7 を束ねて「連鎖」として検知） |
| R7 | 多数のツールを短時間に連続実行（ローカルLLM型でも残る核） |
| ③ / ③CSP | **予防**（攻撃面の最小化 / CSP によるスクリプト制御） |
| G1–G6 | **ガバナンス**の監査イベント（権限・承認・ログの健全性） |

## 攻撃・侵入の用語

| 用語 | やさしい説明 |
|---|---|
| 偵察（recon） | 攻撃前の下調べ。開いているポートや管理画面を探す。 |
| RCE（遠隔コード実行） | 攻撃者がネット越しに、サーバ上で**自由にプログラムを動かせる**状態。最も危険。 |
| unauth RCE | **認証なし**で RCE できること。ログインすら不要なので特に危険。 |
| SQLi（SQLインジェクション） | 入力欄から DB に不正な命令を混ぜ込み、中身を盗む・認証を回避する攻撃。 |
| XSS | 他人のページに悪意あるスクリプトを実行させる攻撃。 |
| skimmer（Magecart） | 決済ページに仕込まれ、**カード番号を盗む**不正スクリプト。 |
| Webシェル | 攻撃者がサーバに置く「遠隔操作用の裏口プログラム」。 |
| 権限昇格（privilege escalation） | 一般ユーザー権限から管理者（root）へ上がること。`sudo NOPASSWD` などが穴になる。 |
| 横移動（lateral movement） | 1台を乗っ取った後、社内の別のサーバへ広げていくこと。 |
| 永続化（persistence） | 再起動後も居座れるよう仕込むこと（cron や systemd timer など）。 |
| C2（指令通信 / Command and Control） | 攻撃者が乗っ取った機器へ指示を送る通信路。チャットツール等が悪用される。 |
| egress（出口通信） | サーバから**外へ出ていく**通信。ここを許可リストで絞ると C2 や情報持ち出しを止めやすい。 |
| VMエスケープ（VM escape） | 仮想マシンの中から抜け出し、土台のホスト（ハイパーバイザ）を乗っ取ること。 |
| ランサムウェア | データを暗号化して身代金を要求する攻撃。バックアップまで消しにくる。 |

## 守りの仕組み・ツール

| 用語 | やさしい説明 |
|---|---|
| CSP（Content Security Policy） | ページが読み込めるスクリプトの出どころを制限する設定。skimmer 対策の要。 |
| Report-Only | CSP を「違反を記録するだけ（ブロックしない）」で試すモード。本番適用前の安全な検証に使う。 |
| SRI（Subresource Integrity） | 外部スクリプトが改ざんされていないかを指紋で確認する仕組み。 |
| FIM（ファイル改ざん検知） | 重要ファイルの変更・新規設置・削除を見張る仕組み。「カーネルレベル」はOSの通知機能でリアルタイムに捕まえる。Wazuh では Syscheck。本リポ記号では R5。 |
| eBPF | Linux カーネル内で安全にプログラムを動かす技術。低負荷で挙動を監視できる（Falco などが利用）。 |
| WORM（Write Once Read Many） | 一度書いたら消せない保存方式。ランサム対策になる。例：オブジェクトストレージの Object Lock／不変化（AWS S3 Object Lock・Azure 不変BLOB・GCP Bucket Lock・WORM NAS 等）。Windows の VSS は管理者権限で消せるので“真のWORM”ではない。 |
| MFA / 2FA / OTP | 多要素認証。パスワードに加え、ワンタイムコード等で本人確認を強める。OTP を平文保存すると意味が薄れる。 |
| IAM | クラウドの「誰が何をできるか」の権限管理。広すぎると1台破られただけで全体に波及。 |
| NFS / no_root_squash | ファイル共有の仕組みと、その危険な設定。`no_root_squash` があると共有先の root 権限が通ってしまう。 |

## 診断・運用の基盤

| 用語 | やさしい説明 |
|---|---|
| SOC | セキュリティ監視を行うチーム／部門。 |
| SIEM | ログを集めて相関・検知する基盤（例：Elastic、Splunk）。R1–R7 のルールはここに載る。 |
| EDR | 端末・サーバ上で不審な挙動を検知・対応する仕組み。 |
| Sigma | ベンダに依存しない検知ルールの共通フォーマット。各 SIEM 用に変換して使う。 |
| Falco | コンテナ/ホストのランタイム挙動を検知する OSS（eBPF 利用）。 |
| Elastic / Datadog | ログ分析・監視の基盤。本リポの `summarize.py` はこの形式でも出力できる。 |
| Semgrep / Trivy / gitleaks | コード診断 / 脆弱性・設定・秘密情報スキャン / 秘密情報検出の各ツール。 |
| ZAP / nmap | Web アプリ診断 / ポートスキャンの定番ツール。 |
| SARIF | 静的解析結果の標準フォーマット。CodeQL などが出力、`vuln_triage` が取り込める。 |
| zgrab2 | ZMap プロジェクトのアプリ層スキャナ。対象へ実際に接続して、バナーや TLS などの応答を JSON Lines で記録する。許可範囲の制限は持たないので、自分の資産だけに使う（`scripts/zgrab2_guard.py` で対象を絞る）。 |
| JSON Lines | 1 行に 1 つの JSON を並べた形式（zgrab2 などが出力）。`vuln_triage` はそのまま読める。 |

## 脆弱性・公開情報の用語

| 用語 | やさしい説明 |
|---|---|
| CVE | 公開された脆弱性に付く世界共通の番号（例：CVE-2026-59310）。 |
| CVSS | 脆弱性の深刻度スコア（0〜10）。9.0 以上は Critical。 |
| セキュリティアドバイザリ | ベンダが出す「この製品にこの脆弱性があります／直し方」の公式告知。 |
| VMSA | VMware（Broadcom）のアドバイザリの名前（例：VMSA-2026-0006）。 |
| GHSA | GitHub のアドバイザリ。ライブラリの脆弱性でよく見る。 |
| Dependabot | 依存ライブラリの既知脆弱性を自動で見つけて教えてくれる仕組み。 |
| 管理面（management plane） | 機器やサービスを管理するための入口（例：vCenter、ESXi、VAMI、BMC/IPMI）。ここの unauth RCE は特に危険。 |

## サンドボックス関連

| 用語 | やさしい説明 |
|---|---|
| サンドボックス | 隔離された使い捨ての実行環境。壊しても本体に影響しない。 |
| ephemeral（使い捨て） | 起動のたびに新品を作り直し、終了で破棄される性質。居座り（永続化）を防ぐが、弱点そのものは消えない。 |
| re-instantiate ≠ re-implement | 「毎回立ち上げ直す」≠「毎回作り直す（コードを書き直す）」。固定のレシピから新品を作るだけ、という意味。 |

## MITRE ATT&CK（補足）

**サイバー攻撃の手口を分類した“事実上の世界標準”。** T番号はその中の各手口に振られた共通コード。

- **MITRE**（米国の非営利組織）が公開・維持。**無料・オープン**で誰でも使える。
- 実際に観測された攻撃の手口を体系的にカタログ化したもの。**SOC・EDR・SIEM・脅威インテリ**のほぼ全ベンダー/現場が共通言語として使う。
- 構造：**Tactics（戦術＝目的、`TA####`）** の下に **Techniques（技術＝手口、`T####`）**、さらに **Sub-technique（`T####.###`）**。
  - 例：戦術「Command and Control」の下に、技術 `T1071 Application Layer Protocol`、その下に `T1071.001 Web Protocols`。

### 本リポの R1–R7 との対応（主なもの）

> **R1–R7 は本リポ独自の整理ラベル**（有名な標準ではない）。中身の“挙動”と MITRE ATT&CK の対応は確立済み。
> 対外的に説明するときは、R番号だけでなく **ATT&CK の T番号を併記**すると世界共通で通じる。完全な対応表は [`defense-detection-notes.md`](defense-detection-notes.md) の §3 参照。

| T番号 | 手口（ざっくり） | 戦術 | 本リポの R |
|---|---|---|---|
| T1595 | Active Scanning（外から能動的に探る偵察） | 偵察 | R3 |
| T1046 | Network Service Discovery（内部のサービス探索） | 探索 | R3 / R2 |
| T1059 | Command and Scripting Interpreter（コマンド/スクリプト実行） | 実行 | R7 / R2 |
| T1071 | Application Layer Protocol（アプリ層プロトコルでの C2） | C2 | R4 |
| T1053 | Scheduled Task/Job（cron/timer での永続化） | 永続化 | R5 |

### なぜ「併記すると強い」のか
- **R4 だけだと本リポの人にしか通じない**が、**`T1071`** と書けば、世界中のアナリスト・製品・ドキュメントと**そのまま突き合わせられる**（共通言語）。
- 逆に ATT&CK は「手口の辞書」であって、**具体的な検知ルールや製品ではない**（＝“何を見るべきか”の地図で、“どう書くか”は Sigma/Falco 等が担う）。
- だから **R1–R7（具体ルール）× ATT&CK（共通分類）は役割が違い、両方あると噛み合う**。

### 注意（過大評価しないために）
- ATT&CK は**網羅的な正解表ではなく、観測された手口の整理**。載っていない手口もあり、1つの攻撃が複数 T に跨ることも普通。
- 「ATT&CK に対応づけた＝守れている」ではない。**“どの手口を見ているか/見ていないか”を棚卸しする地図**として使う。手口の辞書であって、具体的な検知ルールや製品ではない（“どう書くか”は Sigma/Falco 等が担う）。
