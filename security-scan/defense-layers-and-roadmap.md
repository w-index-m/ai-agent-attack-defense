# 防御の4層と導入ロードマップ（予防・検知・応答・復旧）

外部資料（ある提案の「第10章 導入ロードマップと緊急度別チェックリスト」）の対策案を、
このリポジトリの検知/防御タグ（R1–R7 / ③）・攻撃連鎖に対応づけて整理したもの。
**検知・防御の設計に限定し、攻撃の実行手順や安全機構の回避方法は含まない。**

関連: [`defense-detection-notes.md`](defense-detection-notes.md)（検知ロジック本体）/
[`../shared/taxonomy.json`](../shared/taxonomy.json)（タグ・攻撃連鎖の唯一の定義）／ [`defense-playbook.ja.md`](defense-playbook.ja.md)（攻撃連鎖の段ごとの具体化）

---

## 1. 「対策」は R1–R7 だけではない — 4つの層

R1–R7 は対策全体ではなく、**「検知（見つける）」の7パターン**にあたる。
対策は次の4層で1セットになる。R1–R7 だけでは「見つけるが、防げない・戻せない」状態になる。

| 層 | 意味 | このリポの記号 |
|---|---|---|
| **予防** | 攻撃を成立させない（攻撃面を減らす・塞ぐ） | **③ / ③CSP**（＋`defense-detection-notes.md` §5 予防策） |
| **検知** | 起きたことを見つける | **R1–R7** |
| **応答** | 見つけたら止める・封じ込める | 自動 IP BAN・プロセス/コンテナ遮断・隔離 |
| **復旧** | 壊されても元に戻す | 不変（WORM）バックアップ・復元テスト |
| （横断）| 権限・監査の健全性 | **G1–G6**（ガバナンス層） |

R1–R7（＝検知の中身）の早見は [`README.ja.md`](README.ja.md) を参照。

## 3. 評価 — 良い点

- **多層防御として筋が通っている**：予防→検知→応答→復旧が揃い、連鎖③（アップロード→Webシェル）を
  2方向（実行無効化＋読取専用）で塞いでいる。
- **WORM バックアップ**は、本リポのノートに薄かった「復旧・耐改ざん」を補う良い追加。
- 採用 OSS（CrowdSec / Wazuh / Falco）は実績のある定番。

## 4. 注意点 — 鵜呑みにすると事故る/過大評価な箇所

1. **CSP「即日1–2時間」は楽観的**。難所はヘッダ1行でなく、読み込み元の棚卸し・検証・決済代行スクリプトとの両立。
   → まず `Content-Security-Policy-Report-Only` で検証してから本番。本命は**決済代行のホスト型フィールド**
   （カード情報が DOM に乗らない構成）。
2. **Windows VSS は真の WORM ではない**。管理者権限で削除可能で、ランサムは定番で消す。
   オブジェクトストレージの不変化（例: S3 Object Lock の compliance モード、Azure 不変BLOB、GCP Bucket Lock、WORM NAS）は本物の不変。VSS を同列に置かない。
   → 別アカウント／オフライン／MFA 削除＋**復元テスト**まで含めて意味を持つ。
3. **`chmod -R 644` は技術的に誤り**。ディレクトリは実行（traverse）ビットが要るため一括 644 で入れなくなる。
   → 「ファイル 644・ディレクトリ 755」。キャッシュ/セッション等の書込が要る場所は除外。
4. **自動 IP BAN は AIエージェントに過信禁物**。ローカルLLM型・分散IP・低速攻撃には効きにくく、誤BANの副作用も。
   → allowlist・レート制限とセットで、単独の砦にしない。「AI探索を検知」は挙動ベースBANの別名。
5. **クライアントサイド DOM 監視は“検知”で、監視JS自体も改ざん対象**になり得る。
   → 主役は CSP＋SRI、これは補助、の順序を守る。
6. **「自律隔離（自動遮断）」は自爆リスク**。誤検知で本番を自分で止めかねない。
   → 最初は**アラートのみ**、破壊的な隔離は人の承認を挟む段階導入。

## 5. この案に“足りていない”もの（本リポ側が補う）

この案は **Web/ホストのハードニングに強い一方、egress（出口）とアイデンティティが手薄**。

- **R1 / R4**：サーバから外部 LLM / メッセージングへの通信の allowlist・検知（本リポの**最優先**）。
  ローカルLLM型でも **R7** で捉える発想もこの案にはない。
- **連鎖⑥**：IAM 最小権限・Secrets Manager の絞り込み。
- **連鎖②⑤**：OTP/秘密情報の保存方法、データベースのネット直結遮断。

→ **「この案（予防・復旧）＋本リポのノート（egress検知 R1/R4・特権 R2・相関 R6・IAM/秘密情報）」で1枚**にすると穴が埋まる。

## 付録: クラウド/環境別の対応（製品名は変わる、役割は共通）

本リポのツール（netcheck / vuln_triage / detections）は**クラウド非依存**。AWS 固有ではない。
一部の例に AWS 名が出るのは、元の Gambit 事例が AWS だったため。**役割は共通で、製品名が環境ごとに変わるだけ**：

| 役割 | AWS | Azure | GCP | オンプレ/汎用 |
|---|---|---|---|---|
| 不変バックアップ(WORM) | S3 Object Lock | Blob 不変ストレージ(immutability) | Cloud Storage Bucket Lock / 保持ポリシー | WORM対応NAS・テープ・Veeam immutable・MinIO Object Lock |
| 権限管理(IAM) | AWS IAM | Entra ID + RBAC | Cloud IAM | Active Directory/LDAP + 最小権限 |
| 秘密情報管理 | Secrets Manager | Key Vault | Secret Manager | HashiCorp Vault |
| 監査ログ | CloudTrail | Azure Monitor / Activity Log | Cloud Audit Logs | SIEM(Elastic 等)へ集約 |

> 攻撃連鎖⑥の「IAM 全取得」「Secrets Manager 全件取得」も、上の対応で読み替えれば各環境に当てはまる。
> 検知ルール R1–R7 も、クラウドの監査ログ(CloudTrail/Activity Log/Audit Logs)やホスト/ネットワークのログに載せ替えて使う。

## 付録: カーネルレベル FIM とは

**FIM = File Integrity Monitoring（ファイル改ざん検知／完全性監視）。**
重要ファイル（Webプログラム・設定・システム実行ファイル等）の“指紋”（ハッシュ）を記録しておき、
**中身の変更・新規設置・削除・権限変更**を検出して警告する仕組み。
攻撃者の**Webシェル設置**や設定書き換えがここで引っかかる。

- **「カーネルレベル」の意味**：定期スキャン型（○分おきに比較）ではなく、OS の核が持つ
  「ファイル変更をその瞬間に通知する機能」を使う（Linux: audit/fanotify/inotify、Windows: カーネルの
  ファイルフィルタドライバ）。**リアルタイムに捕まえ、すき間の見逃しが減り、負荷も軽い**。
  Wazuh ではこの機能を **Syscheck** と呼ぶ。
- **「自動遮断」**：検知した瞬間に、プロセス停止・IP 遮断などの対応（Wazuh の Active Response 等）まで自動で走らせること。
- **本リポの記号では R5（永続化の新規作成）**に相当。
- 注意：**検知であって予防ではない**（置かせない ③ と併用）。正規デプロイでの誤検知に備えた除外設定が必須。
  自動遮断は自爆リスクがあるので**アラートのみから段階導入**。管理者権限を取られると監視/ログ自体を止めにくる
  （**G4 監査ログの欠落・改ざん**）ので、**ログは別サーバへ送って保全**する。
