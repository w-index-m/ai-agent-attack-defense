# LLM・AI エージェントの防御チェックリスト

English: [`llm-defense-checklist.en.md`](llm-defense-checklist.en.md)

[`llm-target-attacks.ja.md`](llm-target-attacks.ja.md) の 4 類型（プロンプトインジェクション、
システムプロンプト漏洩、間接的プロンプトインジェクション、LLMjacking）の「予防」「検知」の項目を、
**自分のシステムで守られているかを確認する、実行可能なチェックリスト**にしたもの。

> 方針は同じ：**検知・防御の点検に限定**。攻撃の再現手順は含めない。
> 各項目は、環境によって当てはまらない場合がある（例：外部コンテンツを読み込まない LLM アプリには、C は当てはまらない）。
> **自動で判定するスクリプトではない。** 汎用的な静的解析では誤検知・見逃しが多く、環境ごとに実装が違いすぎるため、
> 人が確認する形にした。これも正直さの一部。

## A. プロンプトインジェクション → エージェントの権限での実行

- [ ] エージェントが生成した文字列（ツールの引数、プロンプトの出力）を、**シェルコマンドや `eval` 系の実行に、そのまま渡していない**。
- [ ] **ファイルパスを引数に取るツール**（ダウンロード・アップロード・読み書き）が、渡されたパスを**許可リストで検証**し、意図したディレクトリの外を指せないようになっている（CVE-2026-25592 のパストラバーサルと同じ穴が無いか）。
- [ ] ツール呼び出しが**許可リスト化**されており、エージェントが任意のツール・任意のコマンドを呼べない。
- [ ] エージェントの実行環境が**最小権限**で動いている（コンテナの非 root 実行、不要な capability を外す、ホスト全体への書き込み権限を持たない）。
- [ ] リスクのある操作（ファイル削除、外部送信、認証情報へのアクセス、決済など）に、**人の承認ゲート**が入っている。
- [ ] エージェントのプロセスから、**想定外の子プロセスが起動していないか**を監視している（R7/R8 と同じ発想）。
- [ ] MCP サーバーなど、**外部から指示を受け取る経路**（カスタム指示、プラグイン設定など）に、変更の監査ログがある（G1・G4）。

## B. システムプロンプトの漏洩

- [ ] システムプロンプトに、**認証情報・内部 URL・他のユーザーの情報など、漏れて困るものを書いていない**。
- [ ] 「システムプロンプトはいずれ漏れうる」という前提で、**漏れても実害が無いように設計**されている。
- [ ] 出力に、システムプロンプトの一部がそのまま含まれていないかを見る、**出力フィルタ・検査**がある。
- [ ] 同一の送信元から、**少しずつ内容を変えた質問が、短時間に繰り返される**動きを検知できる（R3 と同じ発想）。

## C. 間接的プロンプトインジェクション（外部コンテンツ経由）

- [ ] LLM が読み込む**外部コンテンツ（メール、Web ページ、文書、他のツールの出力）を、常にデータとして扱い、指示として扱っていない**（最も重要な項目）。
- [ ] 外部コンテンツ内の、**人の目には見えない指示**（HTML コメント、白地に白文字、ゼロ幅文字など）を、LLM に渡す前に取り除く処理がある。
- [ ] LLM・エージェントが**送信できる先（ドメイン、ツール、API）を許可リストで絞って**おり、任意の宛先に送れない（R1/R4 の発想を、エージェント自身の送信に適用）。
- [ ] LLM が生成した**外部リンクやメール本文に、機密情報らしきパラメータが含まれていないか**を確認する仕組みがある。
- [ ] LLM・エージェントのサービスアカウントから、**普段使わないドメインへの送信**を検知できる。

## D. LLMjacking（クラウド認証情報の窃取・不正利用）

- [ ] クラウドの IAM が、**使う LLM サービス・モデルだけに絞った最小権限**になっている（`*` を使った広い許可をしていない）。
- [ ] 認証情報を、コードや設定ファイルに**書いていない**（gitleaks などで確認済み）。
- [ ] クラウドの LLM 利用（推論の呼び出し回数、コスト）に、**予算アラート**を設定している。
- [ ] クラウド監査ログで、**ログ記録の設定を止める操作そのもの**を検知できる（G4。`DeleteModelInvocationLoggingConfiguration` のような操作の実例は `llm-target-attacks.ja.md` §5 を参照）。
- [ ] 不要になった API キー・認証情報を、**定期的に棚卸しして無効化**している。

## 使い方

- 1 回だけでなく、**新しい LLM アプリ・エージェントを追加するたびに**見直す。
- チェックが付かない項目は、`llm-target-attacks.ja.md` の該当する類型（A〜D）の「予防」「検知」の節に、より詳しい説明がある。
- このリポジトリの既存ツールとの対応：
  - A（ファイルパスの検証、許可リスト）→ 自分のコードの確認は `patch_suggest.py`、`vuln_triage.html`（Semgrep の取り込み）
  - A（監査ログの有無）→ G1・G4 の考え方（`defense-detection-notes.md` §7）
  - D（認証情報の棚卸し）→ `gitleaks`（CI）
  - D（クラウドの IAM の最小権限）→ Gambit 連鎖⑥の対策（`defense-playbook.ja.md`）と同じ
