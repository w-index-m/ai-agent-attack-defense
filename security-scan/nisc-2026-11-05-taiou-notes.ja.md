# 「個人情報の漏えい等につながる不正アクセスへの対策について」(2026-11-05、内閣官房国家サイバー統括室)のまとめと本リポジトリとの対比

> 元文書: `https://www.cyber.go.jp/pdf/press/261105_taiou.pdf`(事業者向け、全13ページ)。
> このセッションのネットワーク制限で、一次情報には直接アクセスできなかった。本書は、ユーザーが
> 共有したスクリーンショット(全13ページ分)の文字起こしに基づく。本文は転記ではなく要約。

## 0. 文書の基本情報

- タイトル: 個人情報の漏えい等につながる不正アクセスへの対策について 〜ウェブサイトやモバイルアプリに関する基本的な対策の徹底〜
- 日付: 2026年11月5日
- 発表: 内閣官房国家サイバー統括室(旧 NISC)
- 対象: 事業者向け(経営層〜IT・サイバーセキュリティ担当者)
- 構成: 経営層向けの柱書(考え方)＋ IT・サイバーセキュリティ担当者向けの具体的な対策例、という二層構成。

## 1. 背景(柱書の要旨)

- 相次ぐ不正アクセスによる情報漏えい事案で、モバイルアプリのセキュリティ対策不足・Webサイトの設定不備・
  サポート終了ソフトや既知の脆弱性の放置など、**基本的な対策の不備**が原因とみられる事例を複数確認。
- 攻撃者は、国内のWebサイト等を**大規模に調査**し、侵入方法が見つかったサイトを狙う。**調査や侵入にAIを
  使っている可能性が高く**、従来は「リスクが低い」とされていた弱点の組み合わせが侵入原因になった事例もある。
- 攻撃の大規模化が容易になり、**事業規模を問わず幅広い事業者が標的**になっている。

## 2. 対策の全体構成

### 2.1 運用・管理段階

| 項目 | 要旨 | 対策例(抜粋) |
|---|---|---|
| (1) デジタル資産の把握・脆弱性の解消 | OSS含む構成情報の把握、脆弱性情報の継続収集 | SBOM/SCA、CISA KEV・NVD・JVN/IPAの継続照合、対応の優先順位づけ、緩和策の実施・是正状況管理 |
| (2) アタックサーフェスの棚卸し・最小化 | 推測されやすい認証情報での管理画面侵入、デバッグ用エンドポイントの意図しない公開 | ASM(Attack Surface Management)での把握、不要な公開機能の停止、継続的な外部露出監視 |
| (3) AI活用等による継続的な脆弱性診断・不審な挙動の監視 | **攻撃側のAI活用(脆弱性探索・攻撃手順の自動化)への懸念**を明記。防御側もAI活用を積極的に検討すべきとしつつ、**「AIによる評価結果は根拠・妥当性を確認し、最終判断は人が行う」**と明記 | AIを活用した診断ツールの検討、SOC/SIEM/EDR、AIによる異常検知、SOAR |

### 2.2 設計・開発段階

| 項目 | 要旨 | 対策例(抜粋) |
|---|---|---|
| (1) セキュリティ・バイ・デザイン | 要件定義からのセキュリティ組み込み | 脅威モデリング、ゼロトラスト、管理境界の分離(設計)、SAST・SCA(実装)、DAST・IAST(テスト) |
| (2) 利用するAPIのセキュリティ対策 | NICTの「A2B(App-to-Backend)攻撃」注意喚起に言及。公開アプリの解析からAPIの脆弱性・認可不備を特定し、バックエンドから窃取する事例 | 認可不備の排除(BOLA・BFLA)、認証情報の安全な管理(シークレットマネージャー、CI/CDでのスキャン)、APIのレート制限(複数IP・複数アカウントも含めた異常検知) |
| (3) 公開前の脆弱性診断 | SQLi・OSコマンドインジェクション・RCE・SSRF・ディレクトリトラバーサル等の悪用事例 | セキュリティ基準の設定(リスクベースのリリース可否判断)、第三者ベンダー選定(自動診断に加え手動検証・業務ロジック診断の確認) |

### 2.3 サプライチェーンを通じた侵害への対策

| 項目 | 要旨 | 対策例(抜粋) |
|---|---|---|
| (1) 委託先の統制・接続経路の厳格化 | 委託先環境を足掛かりにした侵入事例。個人情報保護法25条の委託先監督義務に言及 | MFAの適用・接続元IP制限、契約でのセキュリティ要件明確化(インシデント通知義務、SCS評価制度)、ゼロトラストに基づくアクセス制御 |
| (2) OSS・外部ライブラリの適切な管理 | 「深刻な脆弱性は、公表後短期間で悪用されうる」 | 深刻な脆弱性公表時の初動対応手順の明確化(EOL状況の把握、NVD/JVN照合)、委託開発におけるSBOMの提出と確認 |

### 2.4 結び

上記は昨今の攻撃手口に焦点を当てたもので、VPN機器の脆弱性狙い・標的型メール・DDoS、**AIの悪用の高度化**も
想定した対策が必要。経営トップの判断の下、リスク評価に基づく対策強化を要請。

### 2.5 参考資料(抜粋)

SBOM手引(経産省)、CISA SSVC、ASM導入ガイダンス(経産省)、OWASP API/Mobile Top 10、
NICT「A2B攻撃」注意喚起、個人情報保護法ガイドライン、SCS評価制度、JVN、政府機関等の統一基準 等、計23件。

## 3. R1–R7 との対比

> **前提として明記すること**: R1–R7 は、**自律型 AI エージェントが能動的に攻撃している最中の挙動**を、
> ホスト/ネットワークのログから検知するための、振る舞いベースのシグネチャ(`shared/taxonomy.json` が唯一の定義)。
> 一方、NISC の本文書は、主に**事業者側が平時から整えるべき予防・ガバナンス策**(SBOM、ASM、SAST/DAST、
> 委託先統制)を扱っており、両者は**同じ分類体系ではない**。そのため、1 対 1 で綺麗に対応するわけではなく、
> 「関連が強い」「関連が薄い、または対象外」を正直に分けて示す。

| NISC の項目 | R1–R7 との関係 | 説明 |
|---|---|---|
| 1-(3) AIの活用等による継続的な脆弱性診断・不審な挙動の監視 | **R1・R6・R7 と直接関連** | NISC が名指しする「調査・侵入へのAI利用」は、まさに R1(サーバ系からLLM APIへの外向き通信)・R7(多数のセキュリティツールの短時間連続実行)の検知対象そのもの。複数の兆候を束ねる考え方は R6(相関検知)と同じ方向性 |
| 1-(2) アタックサーフェスの棚卸し・最小化(ASM) | **R3 と関連(裏表の関係)** | NISC の ASM は「自組織が、攻撃者より先に自分の公開資産を洗い出す」予防策。R3(偵察的Webアクセス)は、「攻撃者が実際に行う列挙バーストを検知する」側。同じ対象(Webの公開範囲)を、予防側と検知側から見ている関係 |
| 2-(2) APIのレート制限(複数IP・複数アカウントも含めた異常検知) | **R3 と考え方が近い** | 「単一IPだけでなく、複数の送信元・複数アカウントにまたがる異常を見る」という設計思想は、本リポジトリが2026-11-06に追加した R30(プロキシローテーションの検知)にも近い |
| 3-(1) 委託先の統制・接続経路の厳格化 | **R2・R5・R7 と間接的に関連** | 委託先経由で侵入された後の挙動(特権コンテナの起動、永続化、多数ツールの連続実行)は、R2・R5・R7 でそれぞれ検知しうる。ただし NISC の主眼は「侵入させない契約・接続経路の設計」であり、侵入後検知のR1–R7とは層が異なる |
| 1-(1) デジタル資産の把握(SBOM/SCA) | **R1–R7 の対象外** | 予防・資産管理の領域。本リポジトリでは `dep_cve_check.py`(2026-11-06にMaven対応を追加)が対応するツール面の話で、振る舞い検知ではない |
| 2-(1) セキュリティ・バイ・デザイン | **R1–R7 の対象外** | 設計段階の予防策。検知の対象になる「挙動」がまだ存在しない段階 |
| 2-(3) 公開前の脆弱性診断(SQLi・RCE・SSRF等) | **R1–R7 の対象外** | DAST・ペネトレーションテスト的な予防策。本リポジトリでは `sqli-lab`・`auto_vuln_scanner.py` が対応する領域で、R1–R7(侵入後の挙動検知)とは別の層 |
| 3-(2) OSS・外部ライブラリの管理(SBOM提出・EOL把握) | **R1–R7 の対象外** | 1-(1) と同じく予防・資産管理の領域 |
| — (NISC文書に明記なし) | R4(C2的メッセージング)・R8(Webシェル設置) | NISC文書は、侵入後の具体的な通信先(メッセージングAPI等)やWebシェル設置には言及していない。本リポジトリ独自の観測点 |

## 4. リポジトリの既存ツールとの対比

NISC の対策例は「予防・ガバナンス層」が中心なので、R1–R7(検知層)よりも、本リポジトリの**ツール群**
(主に予防・診断系)の方が直接対応する。項目ごとに、実装済み/部分実装/未実装を正直に分けて示す。

| NISC の対策項目 | 本リポジトリの対応ツール | 実装状況 |
|---|---|---|
| 1-(1) デジタル資産の把握・脆弱性の解消(SBOM/SCA) | `scripts/dep_cve_check.py` | **実装済み**。requirements.txt(pip)・package-lock.json(npm、v1/2/3)・packages.lock.json+.csproj(NuGet)に対応し、OSV.dev に照合。Maven対応は2026-11-06に追加 |
| 1-(2) アタックサーフェスの棚卸し・最小化(ASM) | `netcheck/netcheck.py` | **実装済み(自社アセット限定)**。自分のIP・ホストに対する「確認だけ」のポートスキャン・バナー取得。他社・第三者への走査機能は意図的に持たせていない |
| 1-(3) AI活用による継続的な脆弱性診断・不審な挙動の監視 | `ai-sast-trial-notes.md`(診断側)、`detections/`のR1–R31(監視側) | **部分実装 + 知見の蓄積**。AI診断は試行・検証済みだが、「AIの判定は実行ごとにぶれ、本物の脆弱性を誤検知として打ち消すことがある」という**NISCの「AIの評価結果は人が最終判断」という注意と一致する限界**を記録済み。監視側はルールベースのR1–R31(決定的、LLM非依存)で実装 |
| 2-(1) セキュリティ・バイ・デザイン(脅威モデリング・ゼロトラスト) | `scripts/agent_tool_guard.py` | **部分実装**。AIエージェントのツール呼び出し自体を実行前に機械的に検査するガード(許可リスト外ツール拒否、パストラバーサル拒否、クラウドメタデータ拒否、書き込み系は人間承認必須)。design-by-design原則をエージェント実行時に適用した例だが、アプリ全体のSAST/SCA/DASTパイプライン化は未整備 |
| 2-(2) 利用するAPIのセキュリティ対策(認可不備・レート制限) | `security-scan/artex-pattern-lab/`、`detections/r30_*`(プロキシローテーション検知) | **部分実装**。BOLA/BFLA(認可不備)そのものを機械的に検査するツールは無い。複数IP・複数アカウントをまたいだ異常検知の考え方はR30で検知側に実装済みだが、API側のレート制限機構そのものは本リポジトリの対象外(アプリ側の責務) |
| 2-(3) 公開前の脆弱性診断(SQLi・RCE・SSRF等) | `security-scan/sqli-lab/auto_vuln_scanner.py` | **部分実装**。SQLi 8種類中、認証バイパス・エラーベース・UNIONベースの3種類を実測で検出(5/8ペイロードが脆弱版で検出、修正版で誤検知0件)。ブラインド(真偽・時間)・セカンドオーダー・スタックドクエリ・OOBは未実装(前回のSQLiデッキで明示済み)。RCE・SSRFの個別スキャナは無い |
| 3-(1) 委託先の統制・接続経路の厳格化 | — | **未実装**。本リポジトリは自社アセット・自前ラボの検証が対象で、委託先管理・契約統制は範囲外(組織プロセスの話であり、ツール化の対象にしていない) |
| 3-(2) OSS・外部ライブラリの管理(SBOM提出・EOL把握) | `scripts/dep_cve_check.py`、`scripts/os_patch_check_linux.py`/`_windows.py`、`scripts/php_version_check.py`等の各種バージョンチェック群 | **実装済み(自社環境限定)**。深刻な脆弱性公表後の初動(CVE照合)は`crosscheck_osv_ghsa.py`・`ghsa_lookup.py`で対応。SBOMの提出・委託先への要求プロセスは組織運用の話で対象外 |

## 5. 我々ができること(ギャップ分析と次の一手)

優先度の高いものから。

1. **2-(3) 公開前診断の穴を塞ぐ(優先度: 高)**: `auto_vuln_scanner.py` の SQLi は 8 種類中 3 種類の実装。
   ブラインド(真偽・時間)の2種類は検出ロジックの追加だけで実装可能(既にSQLiデッキで検証済みのペイロードが
   ある)。RCE・SSRF用の決定的スキャナは無いため、これが次の実装候補として最も効果が大きい。
2. **2-(2) APIの認可不備チェックの追加(優先度: 中)**: BOLA/BFLA(オブジェクトレベル・関数レベルの認可不備)
   を機械的に検査するツールが無い。`artex-pattern-lab`で検知している「複数IP・複数アカウントでの異常」の
   考え方(R30)を、予防側(診断ツール)にも横展開できる余地がある。
3. **1-(3) AI診断の限界をプロセスに落とし込む(優先度: 中)**: `ai-sast-trial-notes.md`で「AIの判定はぶれる」
   ことは分かっているので、次は**「人が最終確認する」というNISCの要請を、具体的な運用手順(レビュー
   チェックリスト・承認フロー)として明文化する**のが次の一手。ツールの追加実装より、プロセス文書化が先。
4. **3-(1) 委託先統制(優先度: 低、範囲外の可能性)**: 契約・組織プロセスの話であり、ツール化より「チェック
   リスト化」が現実的。本リポジトリのスコープ(所有/認可物の技術的検証)に合うかは要検討で、無理に
   ツール化しない方がよい。
5. **R1–R7側の拡張(優先度: 低、既存課題の継続)**: NISCとの対比で新規に見つかったギャップは無いが、
   既存の既知の限界(R5がSSH鍵の新規作成を拾えない、等)は引き続き未対応。今回の文書との関連では
   新規の優先度変更はしない。

## 6. まとめ

- NISC の対策は、**「侵入させない・侵入しにくくする」予防層**が中心(SBOM/ASM/SAST/DAST/委託先統制)。
- R1–R7 は、**「侵入された後、AIエージェントが活動している最中」を捉える検知層**が中心。
- 両者が明確に重なるのは、**「攻撃側のAI活用」という一点**(1-(3))。NISC が「AIによる評価結果は人が最終判断」と
  釘を刺している点も、本リポジトリの `ai-sast-trial-notes.md` の結論(AIの判定は実行のたびにぶれ、本物の
  脆弱性を誤検知として打ち消すことがある)と一致する。
- 予防層(NISCの主眼)と検知層(R1–R7)は、**補完関係**にある。本リポジトリの既存ツールで言えば、
  `dep_cve_check.py`・`netcheck`・Semgrep・`auto_vuln_scanner.py` が予防層、`detections/` の R1–R31 が検知層、
  という役割分担になる。
- **リポジトリ内ツールとの対比(§4)で見えた最大のギャップは、公開前診断(SQLi全種・RCE・SSRF)の実装の薄さ**。
  次に着手するなら、まずここ。
