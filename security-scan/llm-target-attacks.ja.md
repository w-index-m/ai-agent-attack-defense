# LLM システム自体への攻撃（防御の視点）

English: [`llm-target-attacks.en.md`](llm-target-attacks.en.md)

> ⚠️ **このリポジトリのスコープを広げる文書。** これまでの主題は「**AI エージェントが攻撃に使われる**」（Strix/Cairn/Hermes による Gambit の事例）だった。
> ここからは、「**LLM を組み込んだシステム自体が、攻撃の標的になる**」側を扱う。攻める側ではなく、**自社が LLM・AI エージェントを使っている場合に、守るべき対象**としての整理。
> 方針は変わらない：**検知・防御の設計に限定し、攻撃の再現手順（ペイロード、エクスプロイトコード）は載せない。**

## 1. 対象の 5 類型（一次情報で確認済み）

| 類型 | 一次情報で確認できる事例 | OWASP LLM Top 10 (2025) |
|---|---|---|
| A. プロンプトインジェクション → エージェントの権限での実行 | 下記 §2 | **LLM01**（Prompt Injection）＋ **LLM06**（Excessive Agency） |
| B. システムプロンプトの漏洩 | 下記 §3（PLeak） | **LLM07**（System Prompt Leakage） |
| C. 間接的プロンプトインジェクション（外部コンテンツ経由） | 下記 §4（EchoLeak、および §4.1 の大規模実態調査） | **LLM01** の一種 ＋ **LLM02**（Sensitive Information Disclosure） |
| D. LLMjacking（盗んだクラウド認証情報の不正利用） | 下記 §5（Sysdig、および §5.1 の Double Agents） | **LLM10**（Unbounded Consumption） |
| E. マルチエージェント間のセッション悪用 | 下記 §6（Agent Session Smuggling） | 既存カテゴリに明確に対応なし（エージェント間の暗黙の信頼を突く新しい類型） |

> 本リポジトリの既存の整理（R1–R8、G1–G6）は、**ネットワーク・ホストを観測して、自律型の攻撃エージェントを検知する**ための設計。LLM システム自体を守る層（アプリ内のプロンプト設計、出力の検証）は、観測点が異なる。重なる部分は §7 で示す。

## 2. プロンプトインジェクション → エージェントの権限での実行

一次情報で確認できる事例（いずれも、**特定のベンダー・製品の実装不備**であり、LLM 一般の欠陥ではない）。

| 事例 | 内容（高い粒度） | 出典 |
|---|---|---|
| **EchoLeak**（CVE-2025-32711） | Microsoft 365 Copilot。CVSS 9.3。詳細は §4 | Microsoft、Aim Security |
| **Semantic Kernel — CVE-2026-26030**（Python SDK） | `InMemoryVectorStore` のフィルター機能で、フィルター式の中にアクセスすべきでない危険な属性名を使うことを防げておらず、リモートでのコード実行に至る。CWE-94（コードインジェクション）。CVSS 9.9（Critical）。1.39.4 で修正 | **GitHub Security Advisory（GHSA-xjw9-4gw8-4rqx）を原文で確認済み** |
| **Semantic Kernel — CVE-2026-25592**（.NET SDK、別の脆弱性） | `SessionsPythonPlugin` のファイルのダウンロード/アップロード機能（`DownloadFileAsync`・`UploadFileAsync`）で、渡されたパスの検証が不十分で、任意の場所にファイルを書き込める。CWE-22（パストラバーサル）。CVSS 9.9（Critical）。NuGet 1.71.0・pip 1.39.3 で修正 | **GitHub Security Advisory（GHSA-2ww3-72rp-wpp4）を原文で確認済み** |
| **Context7 MCP サーバー**（CVE-2026-75130） | カスタム指示機能に、毒を仕込んだ指示を入れておくと、連携するコーディングエージェントが、環境変数ファイルから認証情報を盗み、ファイルを削除する、とされる。CVSS 3.1 で 9.0、CVSS 4.0 で 6.4 という、情報源により異なる値が出ている。発見者：Noma Security の Eli Ainhorn 氏。**修正版の有無についても情報源が食い違う**（2.1.3 で修正済みとする情報源と、2026年8月時点で未修正とする情報源がある） | 二次情報（VulnCheck、NVD とも、この環境からは接続できず未確認） |
| **ModelScope ms-agent — CVE-2026-2256** | Shell ツールの入力検証（`check_safe()` 等、呼称は二次情報による）が、プロンプト由来の入力を十分に無害化できておらず、OS コマンドの実行に至る。CWE-77。CVSS 3.1 で 6.5（Moderate）。**2026年3月4日の時点で、修正版は無い（Patched versions: None）** | **GitHub Security Advisory（GHSA-4gc2-344q-r2rw）を原文で確認済み** |

**予防**：
- エージェントが生成した文字列を、**コマンドやコードに動的に組み込まない**（文字列補間・`eval` 系の実行を避ける）。
- **ファイルパスを引数に取るツール**（ダウンロード・アップロード・読み書き）には、渡されたパスを許可リストで検証し、意図したディレクトリの外を指せないようにする（パストラバーサル対策）。
- ツール呼び出しは**許可リスト化**し、エージェントの実行権限を最小限にする（コンテナの非 root 実行、不要な capability を外す）。
- リスクのある操作（ファイル削除、外部送信、認証情報へのアクセス）には、**人の承認ゲート**を挟む。

**検知**：
- エージェントのプロセスから、**想定外の子プロセスが起動する**動き（このリポジトリの **R7**・**R8** と同じ発想：「本来の処理では呼ばれないはずのプロセスが、短時間に呼ばれる」）。
- MCP サーバーなど、外部から指示を受け取る経路への、監査ログの有無（**G1**：スキルの導入・自動生成・自己改変、**G4**：監査ログの欠落・停止）。

### 2.1 フレームワークに依らない一般化した攻撃パターン（Unit 42, CrewAI/AutoGen 実証, 2025-05）

Unit 42 は、CrewAI と AutoGen という2つの異なるオープンソースフレームワークで**機能的に同一のマルチエージェント投資助言アプリ**を構築し、同じ9つの攻撃シナリオを両方に対して実証した。**脆弱性はフレームワーク自体ではなく、安全でない設計パターン・設定ミス・ツール統合側にある**という結論が、本リポジトリの「ツールは中立、設計と統制が要」という立場と一致する。

| シナリオ分類 | 概要（攻撃ペイロードの文言は転記しない） | 主な対策 |
|---|---|---|
| 参加エージェント・システムプロンプト・ツールスキーマの列挙 | オーケストレーターに「委譲せず直接答えろ」等の指示を与え、内部構成の情報を引き出す | プロンプトの堅牢化、コンテンツフィルタ |
| 内部ネットワークへの不正アクセス（SSRF類型） | Web閲覧ツールに、内部プライベートIPへのアクセスを指示 | プロンプト堅牢化、コンテンツフィルタ、**ツール入力のサニタイズ** |
| マウントボリューム経由の機密データ持ち出し | コードインタプリタツールに、ホスト側がマウントしたディレクトリ内の高エントロピー文字列（＝認証情報らしきもの）を探索・Base64エンコードして出力させる | プロンプト堅牢化、**コード実行環境のサンドボックス化**、コンテンツフィルタ |
| クラウドメタデータサービス経由のサービスアカウントトークン窃取 | コードインタプリタツールに、クラウドのメタデータエンドポイント（例：GCPの `metadata.google.internal`）へ特定ヘッダー付きでアクセスさせ、VMのサービスアカウントトークンを取得 | 同上。**本書 §5 の「Double Agents」と同一の攻撃面** |
| SQLインジェクション経由のDBテーブル全体の持ち出し | ツールへの入力にSQLインジェクションのペイロードを混入させ、他ユーザーの取引履歴を含むテーブルを抽出 | プロンプト堅牢化、ツール入力サニタイズ、**ツールの脆弱性スキャン**、コンテンツフィルタ |
| BOLA（破損したオブジェクトレベル認可）による他ユーザーデータへのアクセス | 一見無害な入力（他人のトランザクションID）だけで、バックエンドのアクセス制御不備を突く | ツールの脆弱性スキャン（ペイロード検知では防げない） |
| 間接的プロンプトインジェクションによる会話履歴の持ち出し | 攻撃者が汚染したWebページを、Web閲覧ツールで読み込ませ、埋め込まれた指示に従って会話履歴を外部ドメインへ送信させる | プロンプト堅牢化、コンテンツフィルタ。**本書 §4（EchoLeakと同型の構図）参照** |

Unit 42 が提示する防御の5本柱（詳細は出典を参照）：
1. **プロンプトの堅牢化**：各エージェントの役割・権限を狭く定義し、範囲外の要求を明示的に拒否する指示を入れる。
2. **コンテンツフィルタ**：実行時に入出力を検査するインラインの防御層。
3. **ツール入力のサニタイズ**：ツールは呼び出し元（エージェント）を無条件に信頼しない。型・範囲・特殊文字のチェックを行う。
4. **ツールの脆弱性スキャン**：統合する全ツールに、SAST/DAST/SCAを定期的に実施する。
5. **コード実行環境のサンドボックス化**：コンテナのネットワーク制限（内部サービス・メタデータエンドポイントへのアクセス遮断）、マウントボリュームの最小化、不要なLinux capabilityの削除、危険なシステムコールの禁止、リソースクォータの強制。

**どの対策も単独では不十分**であり、多層防御が必要、というのがUnit 42自身の結論でもある。

## 3. システムプロンプトの漏洩（PLeak）

- **一次情報**：Hui, Yuan, Gong, Burlina, Cao の論文「PLeak: Prompt Leaking Attacks against Large Language Model Applications」（arXiv:2405.06823）。
- **内容**：攻撃者が用意した代替（シャドー）の LLM を使い、**勾配ベースの最適化**で、対象アプリに送る敵対的な質問文を自動生成する。システムプロンプトの先頭から少しずつ、トークン単位で復元していく手法。手作業の質問文や、既存のジェイルブレイクより効果が高いとされる。実際に Poe 上の公開アプリで検証され、著者は Poe に報告している。
- **未確認の点**：この攻撃を「Trend Micro が分析した」「Azure AI Foundry のフィルターを回避した」という記述は、**一次情報（論文、Poe への報告）では確認できなかった**。検索しても、信頼できる一次の Trend Micro の記事は見つからず、転載とみられるページしか確認できていない。この点は、裏付けが取れるまで、事実として扱わない。

**予防**：
- **システムプロンプトに、認証情報や、漏れて困る情報を書かない。** 「システムプロンプトは、いずれ漏れうる」という前提で設計する（秘密の保存場所ではない）。
- 出力に、システムプロンプトの一部がそのまま含まれていないかを検査する、出力フィルタ・分類器を挟む。

**検知**：
- 同一の送信元から、**少しずつ内容を変えた質問が、短時間に繰り返される**動き。このリポジトリの **R3**（偵察的アクセスのバースト検知）と、発想は同じ（対象が Web パスの列挙か、プロンプトの反復質問かの違い）。

## 4. 間接的プロンプトインジェクション（EchoLeak、CVE-2025-32711）

- **一次情報**：Microsoft のセキュリティアドバイザリ（CVE-2025-32711）、Aim Security の報告。CVSS 9.3（Critical）。Microsoft は「AI command injection」に分類し、ネットワーク経由で、認証なしに情報を開示されうるとしている。2025年6月に修正済み。実際の悪用は確認されていないとされる。
- **内容（高い粒度）**：攻撃者が、メールに**隠した指示**（HTML コメントや、白地に白文字など、人の目には見えない形）を仕込んでおく。利用者が、後でまったく別の用件で Copilot に質問すると、**RAG の仕組み**が、そのメールを文脈として読み込んでしまう。隠された指示に従って、Copilot が、手元の機密情報を、外部に送信できる参照リンクに埋め込む。この経路は、Microsoft の防御分類器（XPIA）や、リンクの無害化処理を回避し、Microsoft の正規ドメインを使って情報を持ち出したとされる。Aim Security は、これを「LLM scope violation」（本来の役割の逸脱）と位置づけている。
- **一般化した構図**：LLM が、①外部の、信頼できないコンテンツを読み込み、②その結果をもとに、何らかの行動（送信、ツール呼び出し）を取れる、という組み合わせを持つシステムは、**同じ構図のリスクを持つ**。今回のリポジトリでの用語に合わせると、「取得したコンテンツを、常にデータとして扱い、指示として扱わない」ことが防御の軸になる。

**予防**：
- **外部から取得したコンテンツ（メール、Web ページ、文書）を、指示ではなく、常にデータとして扱う。** これは、このセッション自身が、GitHub の PR やノーティフィケーションの本文を扱う際の原則と、同じ考え方である。
- LLM が外部に送信できる経路（送信先ドメイン、ツール）を**許可リストで絞る**。このリポジトリの **R1/R4**（サーバ系ホストから LLM API・メッセージング API への送信を見る発想）を、「LLM 自身からの送信」に応用したもの。
- 隠しテキスト（HTML コメント、白地に白文字、ゼロ幅文字など）を、LLM に渡す前に取り除く。

**検知**：
- LLM・エージェントのサービスアカウントから、**普段使わないドメインへの送信**（R1/R4 と同じ発想）。
- 生成された外部リンクに、機密情報らしきパラメータが含まれていないかの検査。

### 4.1 Web経由の大規模実態調査（Unit 42, 2026-03-03）

- **一次情報**：Unit 42 の実テレメトリに基づく分析。先行研究の多くがPoC（概念実証）止まりだったのに対し、**実際に野良（in-the-wild）で武器化されている証拠**を初めて大規模に示した点が新しい。
- **内容**：攻撃者はWebページに隠した指示を埋め込み、要約・コンテンツ分析等でそのページを読み込むLLM/エージェントに、意図しない指示を実行させる。Unit 42 はこれを「**攻撃者の意図**」×「**ペイロード工学**」の2軸で分類するタクソノミーを提示：
  - **意図（重大度別）**：低（無関係な出力の強制、良性のスクレイピング対策）／中（採用選考・レビューの偏向操作）／高（AI広告審査の回避、SEO汚染、不正な取引の強制）／重大（データ破壊、機密情報・システムプロンプトの漏洩、サービス妨害＝フォークボム等）
  - **ペイロード配信手法**：視覚的隠蔽（フォントサイズ0、画面外配置、`display:none`、文字色と背景色の同化等）、難読化（SVGのCDATA内への埋め込み、HTML属性への隠蔽）、動的実行（JavaScriptでのランタイム組み立て、Base64の遅延デコード）
  - **ジェイルブレイク手法**：不可視文字の挿入、ホモグリフ置換、ペイロード分割、多言語での指示の反復、JSON/構文インジェクション、**権威を装う社会工学**（「god mode」「開発者モード」等）
- **テレメトリ上の傾向**：攻撃者の意図は「無関係な出力の強制」が28.6%で最多、次いで「データ破壊」14.2%。ペイロード配信は「可視の平文」37.8%が最多（隠す必要すらない、という点が示唆的）。ジェイルブレイク手法は「社会工学」が85.2%と圧倒的多数を占め、技術的な難読化より**説得・権威詐称の方が実際には多用されている**。
- **実際に確認された初の事例**：AIによる広告審査システムを、隠しプロンプトで「この広告は既に承認済み」と偽って通過させようとした実例（2025年12月、Unit 42 が初めて報告）。

**予防（追加）**：
- LLMは、**指示とデータを単一の文脈ストリームの中で区別できない**、という根本的な弱点を前提にする。「スポットライティング」（信頼できないコンテンツと信頼できる指示を明示的に分離するプロンプト設計）のような手法を取り入れる。
- 新しいモデルが備える「instruction hierarchy」（指示の優先順位付け）や敵対的学習も、一定の緩和にはなるが**単独では不十分**。設計レベルの多層防御が必要。

**検知（追加）**：
- 検知システムは、単純なパターンマッチングを超えて、**意図の分析・プロンプトの可視性評価・テレメトリ横断の相関**を組み合わせる必要がある、とUnit 42は結論づけている。

> 本書の方針に従い、具体的な悪性サイトのドメイン名・IOCは転記しない（原典の「Indicators of Compromise」を参照）。

## 5. LLMjacking（盗んだクラウド認証情報での不正利用）

- **一次情報**：Sysdig Threat Research Team の報告（2024年5月、同年9月の続報）。
- **内容**：攻撃者は、**脆弱な Laravel（CVE-2021-3129）**から、クラウドの認証情報を盗み出した。その認証情報で、クラウドがホストする LLM（例：Amazon Bedrock 経由の Claude など）へのアクセス権を有効化し、**他のサイバー犯罪者に転売**した。費用は、被害者のクラウド請求に乗る。Sysdig の見積もりでは、発覚しないまま続けば、1日あたり最大 10 万ドルを超える請求になりうるとしている。9月の続報では、攻撃者が `DeleteModelInvocationLoggingConfiguration` のような操作で、**ログ記録そのものを止めて**、発覚を遅らせようとしたことが報告されている。
- **Gambit の攻撃連鎖との関係**：根本原因は、**Gambit 報告の⑥（Secrets Manager の過剰な権限）と同じ構図**（認証情報の窃取＋過大な権限）。対象が LLM サービスである点が異なるだけ。

**予防**：
- クラウドの IAM を、**使う LLM サービス・モデルだけに絞った最小権限**にする（⑥と同じ対策）。
- 認証情報を、コードや設定ファイルに書かない（gitleaks で検出）。
- コスト・利用量に、**予算アラート**を設定する。

**検知**：
- クラウドの請求・利用量の急な増加（LLM 推論の呼び出し回数の異常）。
- クラウド監査ログで、**ログ記録の設定を止める操作そのもの**を検知する。これは、このリポジトリの **G4**（監査ログの欠落・停止）に、ほぼそのまま対応する実例。

### 5.1 "Double Agents"：GCP Vertex AI の既定権限過多（Unit 42, 2026-03-31）

- **一次情報**：Unit 42 が、自ら構築した Vertex AI Agent Engine 上のエージェントを使った研究。Google と責任ある開示のプロセスで協力し、Google は公式ドキュメントを改訂した。
- **内容（攻撃コードは転記しない）**：Vertex AI にデプロイしたエージェントに紐づく **P4SA（Per-Project, Per-Product Service Agent）** が、**既定で過大な権限**を持っていた。エージェント内のツールから、クラウドのメタデータサービス（`metadata.google.internal`）にアクセスすることで、このサービスエージェントの認証情報（アクセストークン）を窃取できた。
- **窃取した認証情報で到達できた範囲**：①消費者側プロジェクトの Cloud Storage バケットへの無制限の読み取りアクセス、②Google 自身が管理する**制限されたコンテナイメージ（Vertex AI Reasoning Engine の内部実装）**へのアクセス、③テナントプロジェクト内の `code.pkl`（Pythonのpickleファイル＝信頼できない入力の非直列化はRCEリスクがあると公式ドキュメントも警告）を含む機密ファイル。
- **もう一つの構造的弱点**：デプロイ時に割り当てられるOAuthスコープが、**Gmail・カレンダー・Driveなど Google Workspace まで及ぶ広さ**で、かつ既定では編集不可。IAM側の権限が別途必要なため実害は限定的だったが、「最小権限の原則からの設計レベルの逸脱」と Unit 42 は指摘している。
- **Google の対応**：公式ドキュメントの改訂に加え、**BYOSA（Bring Your Own Service Account）**という、既定のサービスエージェントを、組織が用意した最小権限のサービスアカウントに置き換えられる機能を推奨策として提示。本番イメージの改ざん耐性についても確認済みと回答。

**Gambit の攻撃連鎖との関係**：本書冒頭の Sysdig の事例と同じ「クラウド認証情報の窃取によるLLM基盤の不正利用」だが、こちらは**侵入経路が脆弱性の悪用ではなく、クラウドプロバイダ側のサービスが既定で持つ過大な権限**という点で異なる。Gambit 連鎖の⑥（過剰な権限）が、攻撃者の能動的な悪用なしに、**プラットフォームの設計そのもの**から生じうることを示す実例。

**予防（追加）**：
- マネージド型のAIエージェント実行環境を使う場合、**既定のサービスアカウント/サービスエージェントの権限を鵜呑みにしない**。BYOSAのような「自前の最小権限アカウントに置き換える」選択肢がないか確認する。
- OAuthスコープは、IAM権限とは別の層の統制であることを踏まえ、**既定値が広すぎないか**を個別に確認する。

## 6. マルチエージェント間のセッション悪用（Agent Session Smuggling, Unit 42, 2025-10-31）

> これまでのA〜Dは「1つのLLM/エージェントが、悪意あるデータや認証情報の窃取で騙される」構図だった。これは**悪意あるエージェント自身が、正規の通信セッションを使って、別のエージェントを騙す**という異なる構図であり、既存のA〜D分類に明確には収まらないため、別類型として扱う。

- **一次情報**：Unit 42 の研究。A2A（Agent2Agent）プロトコルという、エージェント間通信の標準規格を対象にした、PoC検証（Google ADK/Gemini 2.5で構築した金融アシスタント／リサーチアシスタントの2エージェント構成）。
- **背景**：A2Aは「ステートフル」（直前のやり取りを記憶し、複数ターンにわたる会話を維持できる）な設計を特徴とする。この性質により、連携するエージェント同士は**既定で互いを信頼する**ことが多い。
- **攻撃の核心**：悪意あるリモートエージェントが、正規のクライアントエージェントからのリクエストと、最終的な応答の**間に**、隠れた追加の指示を複数ターンにわたって差し込む。これにより、①コンテキストの汚染、②データの持ち出し、③クライアントエージェント側での無許可のツール実行、のいずれかに至りうる。
- **攻撃が成立する条件（鍵となる性質）**：
  - **ステートフル性**：セッションの状態（会話履歴・変数・タスクの進行状況）を、セッションIDに紐づけて保持する設計であること。
  - **マルチターンのやり取り**：段階的・適応的な攻撃を可能にする（単発のジェイルブレイクより防御が難しいことが知られている）。
  - **自律性・適応性**：AIモデルで駆動されるエージェントは、クライアントの入力や中間応答を見て、動的に指示を作り変えられる。
  - **エンドユーザーから見えない**：この密輸された指示のやり取りは、通常のチャットUIでは最終応答しか表示されないため、**人間には見えない**。
  - MCP（Model Context Protocol）は一般にステートレスでAIモデルを介さないため、この種の多段階・適応的な攻撃は成立しにくい。A2Aのような、永続状態＋モデル駆動の推論を持つプロトコル特有のリスク。
- **PoC① 機密情報の漏洩**：悪意あるリサーチアシスタントが、一見無害な確認質問を段階的に重ねることで、金融アシスタント側のチャット履歴・システム指示・利用可能なツール・ツールのスキーマを引き出すことに成功。
- **PoC② 無許可のツール実行**：同様の手口で、金融アシスタントに`buy_stock`ツールを呼び出させ、ユーザーの同意なしに株式10株分の取引を実行させることに成功。
- **Unit 42 の結論**：A2Aプロトコル自体の脆弱性ではなく、**ステートフルなプロトコル一般が、エージェント間の暗黙の信頼とどう相互作用するか**という、より広い設計上の課題。

**予防**：
- リスクの高い操作には、**モデルが影響を及ぼせない、帯域外（out-of-band）の人による確認**を必須にする（静的なUI要素やプッシュ通知など、生成系の経路を通さない確認）。
- **コンテキスト・グラウンディング**：セッション開始時の、元のユーザー意図に基づく「アンカー」を持ち、以降のやり取りがそのアンカーと意味的に整合しているかを継続的に検証する。大きく逸脱した場合は、ハイジャックの疑いとしてセッションを終了する。
- エージェント間の通信前に、**暗号署名されたAgentCard等による身元検証**を要求する（なりすまし・スプーフィングの防止。ただし、信頼されたエージェント自体が乗っ取られるケースは防げない）。
- クライアントエージェントの内部的なやり取り（ツール呼び出し等）を、**エンドユーザーに見える形で可視化**する（実行ログ・リアルタイムの活動表示等）。

**検知**：
- セッション内で、ユーザーの原意図と無関係な話題・指示への逸脱が、エージェント間のやり取りに含まれていないか（コンテキスト・グラウンディングの技術的な裏付け）。
- クライアントエージェントが、ユーザーの直接の指示なしに、ツール呼び出しを行っていないか（本リポジトリの **R7** と同じ「想定外の多段階実行」という発想を、ネットワーク・ホストではなくエージェント間通信に適用したもの）。

## 7. このリポジトリの既存の整理との接続点

| 今回の類型 | 既存の整理との接続 |
|---|---|
| A. 実行権限の濫用 | R7/R8（想定外のプロセス起動）、G1（スキルの自動生成）、G4（監査ログ） |
| B. システムプロンプト漏洩 | R3（反復アクセスのバースト検知）と同じ発想 |
| C. 間接的プロンプトインジェクション | R1/R4（LLM・メッセージング API への送信の監視）を、エージェント自身の送信に応用。**R9として実装済み**（`detections/sigma/r9_idpi_steered_egress.yml`、`detections/datadog/r9_idpi_steered_egress.json`） |
| D. LLMjacking | Gambit 連鎖の⑥（IAM の過大な権限）と同じ構図、G4（監査ログの欠落・停止）。§5.1のクラウドメタデータサービス経由の資格情報窃取は**R10として実装済み**（`detections/sigma/r10_metadata_service_credential_access.yml`、`detections/datadog/r10_metadata_service_credential_access.json`） |
| E. マルチエージェント間のセッション悪用 | R7（想定外の多段階実行）をエージェント間通信に応用。**R11として実装済み**（`detections/datadog/r11_agent_session_smuggling.json`、ただしアプリ側のツール呼び出しログの計装が前提） |

**A・Bは接続点の指摘のみで、検知ルールの実装ではない**（R7/R8・R3は本来Gambit連鎖＝攻撃エージェント側向けのルールへの間接的な応用であり、専用ルールは作っていない）。C・D・Eは、`security-scan/detections/`にR9–R11として実際のSigma/Datadogルールを追加した（`security-scan/detections/README.md`参照）。R9/R10は標準的なプロキシ/ネットワークログで検知できるが、R11（Agent Session Smuggling）はアプリケーション側でのツール呼び出しログの計装が前提で、汎用的なネットワークシグネチャは存在しない。

## 8. 限界・未確認の点

- Semantic Kernel（2件）と ModelScope ms-agent は、**GitHub の公式 Security Advisory（GHSA）の原文**を、この環境から直接読んで確認した。Context7 は、NVD・VulnCheck ともこの環境から接続できず、二次情報（ニュース記事・脆弱性データベースの転載）のみで、**修正版の有無すら情報源により食い違う**。
- いずれも、**実際に動かして確認したものではない**（原文を読んだだけで、攻撃コードは書いていない）。
- PLeak の「Trend Micro」「Azure AI Foundry」への言及は、**裏付けが取れていない**（§3 参照）。
- LLMjacking の被害額は、Sysdig の見積もりであり、情報源により数字が異なる（他の記事では別の集計期間・金額が出ている）。正確な数字は、Sysdig の一次記事（sysdig.com/blog）で確認すること。
- §2.1（Unit 42, CrewAI/AutoGen実証）、§4.1（Unit 42, Web経由IDPIの実態調査）、§5.1（Unit 42, Double Agents）、§6（Unit 42, Agent Session Smuggling）は、いずれも Unit 42 自身の一次記事を整理したものであり、独自の追加検証は行っていない。攻撃ペイロード・コードは意図的に転記していない。
- §6 の Agent Session Smuggling は、Unit 42 自身が「実際の悪用は未観測（not observed in the wild）」と明記しているPoC段階の研究である。
