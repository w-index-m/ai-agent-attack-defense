# F5 BIG-IP APM OAuth RCE確認（確認専用）

> **CVE-2026-94127の公表日: 2026-09-22**（F5公式アドバイザリ K000162605）。JPCERT-AT-2026-0028は
> 2026-09-24公開(本書 §背景参照)。このノート自体は2026-10-23にこのリポジトリへ追加した。

`scripts/f5_bigip_apm_check.py`: F5 BIG-IP APMのOAuth UserInfoハンドラにおけるヒープベースの
バッファオーバーフロー(CVE-2026-94127、CVSS 9.8、事前認証不要RCE、F5が悪用を確認、CISA KEV掲載。
[`detections/`](detections/) の R23 参照)の対象になりうるか、または侵害の兆候があるかを確認する。

> ⚠️ 方針：**確認だけ**。設定変更、ファイルの書き換え、ネットワークへの送信は一切しない。
> **BIG-IP実機のbashシェル上で実行することが前提**(他の多くの`scripts/*.py`と違い、外部からの
> 能動スキャンではバージョン/ログを確認できないため)。

## 背景: CVE-2026-94127とR23の関係

本ツールは、JPCERT-AT-2026-0028とF5のK000162605が公式に挙げている侵害検出方法を、そのまま
自動化しただけのもの。独自の判定ロジックは追加していない。

F5は2026-09-22、BIG-IP APMのOAuth UserInfoハンドラにおけるヒープベースのバッファオーバーフロー
(CVE-2026-94127)のアドバイザリを公表。APMがOAuth Authorization Serverとして構成され、
仮想サーバーにAPM access policyとOAuth profileが設定されている場合、認証されていないリモートの
攻撃者が任意のコードを実行する可能性がある。F5は本脆弱性が悪用されていると表明。CISA KEV掲載
(2026-09-22、連邦機関の対応期限2026-09-25)。watchTowr Labsが詳細な攻撃手法を公表
(「Is This A Joke? In The Auth Header?」)。影響バージョン: 21系(21.1.0)、17系(17.5.0〜17.5.1、
17.1.0〜17.1.3)。OAuth Client/Resource Serverとしてのみ使っている構成は対象外。

## できること

JPCERT-AT-2026-0028「V. 侵害検出方法」の4点をそのまま自動化:

- `tmsh show sys version`(または`--version`で直接指定)を影響バージョン一覧と照合。
- `/var/log/apm`(既定、`--apm-log`で変更可)からログID`01990004`(OAuth UserInfo要求失敗)を
  集計し、単一送信元IPから10回以上の反復が無いかを確認(JPCERTの目安をそのまま閾値に採用)。
- TMMコアファイル(既定`/var/core/`、`--core-dir`で変更可)の有無を確認。
- `/etc/bigstart/scripts/tmm.finish`のSHA256ハッシュを算出して表示(**既知の正常値との比較は
  行わない** — バージョン/ビルドごとに正規の値が異なるため、本ツールが「これが正常値」と
  決め打ちすることはしない。運用者が自分の構成管理・バックアップの記録と突き合わせること)。
- SARIF 2.1.0 での出力にも対応(`--out`)。`vuln_triage.html` に読み込める。

## できないこと・正直な限界

- **apmログの行フォーマットは実機での裏取りができていない。** 実際のBIG-IPアプライアンスへの
  アクセスがこのセッションには無いため、「ログID `01990004` を含む行から、その行中のIPv4
  らしき文字列を拾う」というベストエフォートの抽出に留めている。実際のログ行フォーマットが
  想定と異なる場合、送信元IPの集計が正しく行われない可能性がある(合成したログでのテストでは
  正しく動作することを確認済みだが、実機ログでの検証ではない)。
- `tmm.finish`のハッシュは算出するだけで、正常/異常の判定はしない(上記のとおり)。
- 他の多くの`scripts/*.py`と違い、**外部からの能動スキャンでバージョンを確定することはしない**
  (BIG-IPはApache/Nginx/BINDと違い、バージョンバナーを出す設計ではないため)。BIG-IP実機、
  またはそこからエクスポートしたログファイルへのアクセスが前提。
- TMMコアファイルの中身は解析しない(存在確認のみ)。

## 使い方

```bash
# BIG-IP実機のbashシェル上で
python3 scripts/f5_bigip_apm_check.py
python3 scripts/f5_bigip_apm_check.py --out f5_apm.sarif

# tmshが無い環境、またはログをエクスポートして確認する場合
python3 scripts/f5_bigip_apm_check.py --version 17.1.2 --apm-log /path/to/exported/apm.log
```

## 検証

- このサンドボックス環境(BIG-IPではない)に対して実行し、`tmsh`/`/var/log/apm`/`/var/core`/
  `tmm.finish`のいずれも見つからない場合に、それぞれ正しく`info`レベルで報告することを確認した。
- バージョン判定: `--version 17.1.2`(影響範囲内)で`high`、`--version 17.1.4`(一覧外)で`info`に
  なることを確認した。
- apmログの集計: 合成したログファイル(単一IPから12件の反復 + 別IPから3件)で`high`判定
  (反復元IPと件数を正しく報告)、1件のみの合成ログで`medium`判定になることを確認した。
- TMMコアファイル検知: ダミーのコアファイル(`tmm.1234.core`)を置いたディレクトリに対して
  `high`判定になることを確認した。
- `tmm.finish`ハッシュ: ダミーファイルに対してSHA256を正しく算出することを確認した。
- **実際のBIG-IPアプライアンス、実際のapmログフォーマットに対しては未検証**(このサンドボックス
  にBIG-IP実機が無いため)。上記の「できないこと・正直な限界」を参照。

> 確認・検知の設計に限定。攻撃の実行手順やエクスプロイトコードは含めない。
