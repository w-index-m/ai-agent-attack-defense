# AI エージェント攻撃 防御プレイブック

English: [`defense-playbook.en.md`](defense-playbook.en.md)

Strix / Cairn / Hermes / ARTEX という、攻撃用 AI エージェントの**動きが分かっている**ことを前提に、
「**自分の環境をどう守るか**」を、攻撃連鎖の段ごとに、予防・検知・応答・確認まで具体化したもの。

> **前提と限界（先に読む）**
> - 相手のツールの情報は、**公開情報と、公開ソースの静的レビュー**（[`artex-analysis.ja.md`](artex-analysis.ja.md)、[`defense-detection-notes.md`](defense-detection-notes.md) など）に基づく。
>   攻撃側が実際にこれらを使うとは限らず、この順で動くとも限らない。
> - **攻撃の手順、兵器化、安全機構の回避は含まない。** 罠（§5）は設計メモで、攻撃側への反撃は扱わない。
> - 対象は**自分が所有・認可した環境**。点検や訓練も、その範囲でだけ行う。
> - このリポジトリに**まだ無い対策は「未実装」と明記**している（§9）。あるように読めてしまう書き方はしない。

---

## 0. 使い方

- **点検**：§3 の「予防」を、自分の環境のチェックリストにする。
- **検知の実装**：§3 の「検知」から、[`detections/`](detections/) のルールへ。無いものは §9 の未実装一覧。
- **事故対応**：§4。**訓練**：§7。
- **まず1週間で何をするか**：§8。

## 1. 相手を知る：4つのツールの「見える動き」

| ツール | 型 | 特徴（解析より） | 主に効く対策 |
|---|---|---|---|
| **Strix** | 偵察・脆弱性探索 | Docker サンドボックスで実行。HTTP をプロキシで捕捉。nmap / ffuf / ブラウザ自動操作を同梱 | 露出の削減、WAF とレート制限、管理画面の隔離（R3） |
| **Cairn** | 探索的侵入 | 黒板サーバ（:8000）と、事実と意図のグラフ。ワーカーのコンテナを多数起動（NET_RAW / NET_ADMIN）。失敗しても別の意図で粘る | コンテナの監視（R2）、内部の分離、egress の絞り込み |
| **Hermes** | 統括・事後 | スキルで拡張。メッセージングアプリ（Telegram など）との接続、cron、サブエージェントの大量生成 | 外向きメッセージング（R4）、永続化（R5）、ガバナンス（G1–G6） |
| **ARTEX** | 計画役と実行役、共有グラフ | 唯一の計画役が意図を作る。通信を記録するプロキシ、MCP、スキル用ディレクトリ。承認ゲートと破壊的操作の拒否を内蔵 | egress（R1、R4）、偵察（R3）、多ツール連続実行（R7） |

**共通点**：頭脳として LLM を呼ぶ（クラウドなら外向きの HTTPS）、多種のツールを短時間に連続して動かす、偵察は大量に列挙する。

### どこに、どう見えるか（ここを取り違えない）
| 見え方 | 状況 | 見える痕跡 |
|---|---|---|
| **1. 受け側の痕跡** | 外から来る偵察や Web 攻撃 | 短時間の大量リクエスト、404 / 403 / 5xx の急増、管理画面への外部アクセス（**R3**、アプリのログ） |
| **2. 足場の上の動き** | 侵入後、あなたのサーバ上でツールやエージェントが動く | LLM API への通信（**R1**）、特権コンテナ（**R2**）、メッセージング（**R4**）、永続化（**R5**）、多ツール連続実行（**R7**） |
| **3. 自組織のエージェント** | 社内で自分たちが攻撃用エージェントを使う | 承認、スコープ、記録（**G1–G6**）。R1 と R7 も、想定外の場所での利用の発見に使える |

- **攻撃側の基盤から出る LLM 通信は、あなたの側には見えません。** 外から攻撃を受けるだけの段階では、見えるのは 1 です。R1・R2・R4・R5・R7 は、足場を作られた後（2）や、社内（3）で効きます。
- **攻撃側がローカル LLM を使うと R1 は出ません。** その場合は R7・R2、受け側の痕跡へ重心を移します。

## 2. 防御の原則（5つ）

1. **見つかる弱点を減らす。** エージェントは列挙が速い。露出と既知の弱点を先に潰す（netcheck、`vuln_triage`、パッチ）。
2. **連鎖の途中で切る。** 攻撃は、各段が成功して初めてつながる。段ごとに別の対策を置く。
3. **機械の速さを検知する。** 人間離れした連続実行や列挙（R7、R3）は、ローカル LLM でも残る。
4. **出口を絞る。** 足場を作られても、外との通信（LLM、C2）が許可リストで止まれば、動きにくい（R1、R4）。
5. **自分のエージェントも統制する。** 承認、権限、記録を持たせる（G1–G6）。

## 3. 攻撃連鎖の7段 × 防御

Gambit の事例の連鎖（定義: [`../shared/taxonomy.json`](../shared/taxonomy.json)）。各段で「予防 → 検知 → 応答 → 確認」を示す。
検知欄の **【未実装】** は、このリポジトリにルールが無いこと（§9）。

### ① ログイン画面の SQL インジェクション
- **予防**：プレースホルダ（パラメータ化クエリ）を使う。ORM でも、生のクエリに変数を埋め込まない。DB 接続のアカウントは、必要なテーブルの必要な操作だけに絞る。WAF とレート制限は補助。
- **検知**：同じ送信元からの短時間の大量リクエスト、エラーの急増（**R3**: [Sigma](detections/sigma/r3_recon_enumeration_burst.yml) / [Elastic](detections/elastic/r3_recon_burst.json) / [Datadog](detections/datadog/r3_recon_burst.json)）。アプリログの DB エラー。
- **応答**：該当エンドポイントの一時停止、ログの保全、送信元の遮断（分散した IP には効きにくい）。
- **確認**：CI の Semgrep で、文字列連結の SQL を探す。検証環境で同じ入力を再テストする。

### ② OTP が DB に平文で保存される（MFA の回避）
- **予防**：OTP はハッシュ化して保存し、5分程度で失効させる。試行回数に上限を付け、超えたらロックする。パスワードは bcrypt / argon2 などの遅いハッシュ。
- **検知**：同じアカウントへの短時間の大量試行、認証の異常。**【未実装】**（認証ログ用のルールは無い）
- **応答**：影響するアカウントの OTP とセッションを失効させ、再発行する。
- **確認**：DB のテーブルを見て、認証に関わる値が平文で残っていないか確認する。

### ③ 管理画面のアップロードに拡張子の検証が無い（Web シェルの設置）
- **予防**：許可する拡張子を許可リストで決め、中身も検証する。保存先は公開領域の外に置き、実行権限を付けない。ファイル名は作り直す。管理画面は VPN や IP 制限の内側に置き、多要素認証を付ける。Web ルートは読み取り専用にする（ファイルは 644、ディレクトリは 755。書き込みが要る場所は除く）。
- **検知**：Web ルートやアップロード先への新規ファイルの設置、Web サーバ配下からの子プロセス起動。**【未実装】**（R5 は cron / systemd の永続化で、Web シェルの設置そのものは見ない。外部の FIM は [`defense-layers-and-roadmap.md`](defense-layers-and-roadmap.md) を参照）。管理画面への外部アクセスは **R3** と netcheck で確認できる。
- **応答**：該当ファイルを、**消す前に**コピーして保全し、隔離する。経路になったアカウントを確認し、認証情報を更新する。
- **確認**：自分の検証環境で、画像以外のファイルを管理画面から上げて、拒否されることを確認する。netcheck で管理画面らしき URL の公開状況を見る。

### ④ sudo がパスワードなしで実行できる（権限昇格）
- **予防**：NOPASSWD をやめ、必要なコマンドだけを個別に許可する。Web アプリの実行ユーザーには sudo を与えない。コンテナは一般ユーザーで動かし、特権と不要な capability をやめる。
- **検知**：特権や NET_RAW 付きのコンテナの起動（**R2**: [Sigma](detections/sigma/r2_privileged_container_spawn.yml) / [Falco](detections/falco/cairn-ai-agent.yaml) / [Elastic](detections/elastic/r2_privileged_container.json)）。sudo の異常な実行は **【未実装】**。
- **応答**：該当ホストを隔離する。アカウントと鍵を失効させ、イメージから再構築する。
- **確認**：実行ユーザーで `sudo -l` を実行して、許可の範囲を見る。

### ⑤ NFS の設定不備と、設定ファイル内の認証情報
- **予防**：`no_root_squash` を外して `root_squash` にし、接続元を限定する（読み取りだけで足りるものは ro）。認証情報は設定ファイルに置かず、環境変数やシークレット管理サービスから渡す。pre-commit と CI で gitleaks を回す。
- **検知**：認証情報ファイルへの異常な読み取り、罠の認証情報の使用（§5）。**【未実装】**
- **応答**：漏れた認証情報は、**直ちに無効化して作り直す。** Git の履歴からも消す（消すだけでは履歴に残る）。
- **確認**：`/etc/exports` を見る。gitleaks を履歴ごと回す。

### ⑥ Secrets Manager の全件取得（IAM が広すぎる）
- **予防**：`*` を使った許可をやめる。アプリごとに、必要な秘密を1つだけ許可する。長期のアクセスキーを避ける。
- **検知**：クラウドの監査ログで、短時間に多数の秘密を取得する動き、通常と違う主体や場所からのアクセス。**【未実装】**
- **応答**：該当の主体の権限を取り消し、キーを無効化する。漏れた可能性のある秘密を、すべて作り直す（優先順は §4.2）。
- **確認**：IAM Access Analyzer などで、使われていない権限と、外部に公開されているものを洗い出す。
- 他のクラウドの対応製品は、[`defense-layers-and-roadmap.md`](defense-layers-and-roadmap.md) の付録を参照。

### ⑦ カード番号の暗号鍵が、同じ環境から取得できる
- **予防**：カード番号を自社で持たず、決済代行のトークン化を使う。鍵は KMS などの別の仕組みに置き、アプリには復号の権限だけを与える。決済ページはホスト型にし、CSP と SRI で、スクリプトの挿入を防ぐ。MD5 / SHA-1 / ECB は使わない。
- **検知**：鍵へのアクセスの異常（KMS の Decrypt の急増、通常と違う主体）。**【未実装】** 決済ページのスクリプトの改ざんは、CSP の Report-Only の報告で気づける。DOM 監視は補助。
- **応答**：鍵をローテーションする。カード会社と決済代行への連絡の要否を確認する。決済ページを一時停止する。
- **確認**：鍵の置き場所と、鍵にアクセスできる権限を一覧にし、データと同じ環境に無いか確認する。netcheck で、決済ページの CSP の有無を見る。

## 4. 検知から応答まで

### 4.1 シグナル別の最初の動き
| シグナル | まず確認すること | 封じ込め |
|---|---|---|
| **R1 / R4**（LLM・メッセージングへの通信） | 送信元ホストの業務上の用途 | 正規でなければ、egress を遮断し、プロセスとコンテナを調べる |
| **R2**（特権コンテナ） | 起動元、イメージの出所、capability の必要性 | 未知のイメージ＋特権は高確度。隔離して停止する |
| **R3**（偵察の列挙） | 対象になった資産の露出（netcheck） | 露出を塞ぐ。続くなら遮断 |
| **R5**（永続化） | 作成したプロセスの系統 | 永続化を除去し、系統を遡る |
| **R7**（多ツール連続実行） | 親プロセスと、実行されたツールの一覧 | R1、R2 と相関させる。単独なら、正規の利用かを確認 |
| **R6**（相関） | 単発を超えた連鎖として扱う | インシデントとして宣言し、§4.2 へ |
| **G1–G6**（ガバナンス） | 該当のエージェントとセッション | セッションを保全し、外側の安全層で拒否する |

### 4.2 インシデントの流れ
1. **初動**：担当を決め、記録を始める。ログ、プロセス一覧、ネットワーク接続を保全する。連鎖の**どの段まで進んだか**の仮説を立てる（①〜⑦）。
2. **封じ込め**：被疑ホストをネットワークから隔離する（電源はすぐ落とさず、保全を優先する）。egress を遮断し、疑わしいアカウントを停止する。
3. **根絶**：永続化（cron、systemd、起動項目）と Web シェルを取り除く。**イメージから作り直す**のが確実。
4. **認証情報の更新**（進んだ段に応じて範囲を決める。優先順）：
   1. クラウドの長期キーと管理者の認証情報
   2. DB とアプリの秘密
   3. Secrets Manager の中の全件（⑥まで進んでいた場合）
   4. 決済の鍵（⑦まで進んでいた場合）
5. **復旧**：復元テスト済みの、不変のバックアップから戻す。パッチを当て、再発しないことを確認する。
6. **通知**：個人情報やカード情報が関わるときは、法令と契約上の通知義務（期限がある場合がある）を、担当者や専門家に確認する。
7. **振り返り**：どの段で検知できたか、できなかったかを記録し、ルールとチェックリストを更新する（手順: [`../shared/README.md`](../shared/README.md)）。

### 4.3 自動化は段階的に
**アラートのみ → 人の承認つきの遮断 → 限定的な自動遮断**の順にする。いきなり自動遮断にすると、誤検知で自分のサービスを止める。
自動の IP 遮断は、分散した IP や、ゆっくりした攻撃には効きにくい。許可リストとレート制限と組み合わせる。

## 5. 罠による検知（ハニートークン）設計メモ【未実装】

**考え方**：本物の業務で使われない偽の認証情報や偽のデータを、自動化された列挙が拾いそうな場所に置く。**使われたら、ほぼ確実に不正**なので、誤検知が少ない警報になる。

| 置き場所の例（段） | 内容 | 警報の条件 |
|---|---|---|
| 設定ファイル、リポジトリの例ファイル（⑤） | 実在しないサービスの偽のキー | そのキーでの認証の試行 |
| Secrets Manager（⑥） | 偽の名前の秘密 | その秘密の取得 |
| DB（①②） | 偽のテーブルや偽のアカウント | 読み出し、そのアカウントでのログイン試行 |
| 偽の管理者アカウント（③④） | 実在しないユーザー | ログインの試行 |

**設計の注意**：
- **本物の認証情報や本物のデータは、絶対に使わない。** 偽物は、実際には何にもアクセスできないようにする。
- 偽物ごとに、**固有の識別子**を付ける（どこから漏れたか分かる）。
- **台帳**に記録し、社内の人が誤って触らないようにする。警報の経路を、実際に試して確認する。
- 本番のデータの品質や業務を邪魔しない。個人情報や契約の観点を確認する。
- **限界**：攻撃側が触れなければ、警報は出ない。**予防ではなく、検知の補助。**

**やらないこと（本書の範囲外）**：攻撃側のエージェントに命令を注入して妨害する、相手の環境へ反撃する、といった**能動的な対抗措置**。法的なリスクがあり、確実でもない。

## 6. 自分の側でエージェントを使う場合（G1–G6）

自組織で攻撃用エージェント（レッドチーム用など）を**認可のもとで**使うなら、次を必須にする。ARTEX が内蔵する仕組みが、よい雛形になる。

- **承認ゲート**：ツールの呼び出しを、許可・拒否・確認で規則化する。破壊的な操作（削除系の API など）は既定で拒否する。
- **スコープの強制**：認可した対象の外へ出られないようにする。
- **記録**：LLM の呼び出しとツール実行を残す。
- **G1**：スキルの導入、自動生成、自己改変を、出所・署名・レビューで統制する。
- **G2、G3**：安全設定の変更や、安全機構の迂回の意図を、外側の安全層で拒否し、記録する。
- **G4**：ログの欠落や停止を検知する（ログ自体への攻撃を疑う）。
- **G5、G6**：権限の拡大は人の承認を必須にし、サブエージェントの数と権限を監視する。

## 7. 確認と訓練（認可された範囲で）

- **露出の点検**：自分の資産に対して netcheck を回す。zgrab2 を使うなら、[`../scripts/zgrab2_guard.py`](../scripts/zgrab2_guard.py) を通して対象を絞る。結果は `vuln_triage.html` で優先度づけする。
- **検知ルールの確認**：検証環境で、**無害な模擬の動き**を作って、警報が出るかを見る。
  例：R3 は自分の検証サーバへ、存在しないパスの大量リクエスト。R7 は、バージョン表示だけの無害なコマンドを、多種連続で実行。R2 は検証環境で、特権付きのコンテナを起動。
- **机上訓練**：§3 の7段を1段ずつたどり、「ここで気づけるか」「誰が何をするか」を声に出して確認する。
- **見る指標**：検知までの時間、封じ込めまでの時間、7段のうち予防と検知がそろっている段の数（§9）。
- **実際の攻撃ツールの実行は、認可された隔離ラボだけ**（手順: [`cairn-lab/cairn-authorized-lab-runbook.md`](cairn-lab/cairn-authorized-lab-runbook.md)）。

## 8. 最初の1週間でやること（優先順）

1. **露出を確認する**：netcheck を、自分の資産に回す。管理面（vCenter、ESXi、管理画面）が外から届いていないか。
2. **秘密情報を棚卸しする**：gitleaks を履歴ごと回す。見つかったものは無効化して作り直す。
3. **外向き通信を絞る**：サーバ系から LLM API とメッセージングへの通信を、既定で遮断する（R1、R4 の前提）。
4. **IAM を絞る**：`*` の許可を探して、必要な範囲に絞る（⑥）。
5. **検知を入れる**：R1、R4、R2 を先に入れ、アラートだけで始める。
6. **復旧を確かめる**：不変のバックアップから、**実際に戻せるか**を試す。

| ① SQLi | Semgrep（CI） | R3 | WAF（運用側） |
| ② OTP | 手動の確認 | **無し** | 認証ログの異常検知 |
| ③ アップロード | netcheck（管理画面の公開）、Semgrep | R3（外部アクセス） | Web ルートのファイル監視（FIM）、子プロセスの監視 |
| ④ sudo | Trivy（設定の指摘） | R2（特権コンテナ） | sudo の異常検知（auditd や EDR） |
| ⑤ NFS・認証情報 | gitleaks、Trivy | **無し** | ファイルアクセスの監査、罠（§5） |
| ⑥ IAM | Trivy（IaC の指摘） | **無し** | クラウド監査ログの検知 |
| ⑦ 鍵・カード | netcheck（CSP の有無） | **無し** | KMS の監査、CSP の Report-Only の収集 |

- **R1〜R7 は、ネットワークとホストの観測が中心**です。②⑤⑥⑦の検知は、アプリ・クラウドの監査ログの層で、**まだ無い**。次の課題。
- **応答（§4）は手順の文書のみ**で、自動化の実装は無い。
- **罠（§5）は設計のみ**で、ルールも実装も無い。
- 実際の攻撃ツールに対して検知できるかの**実機検証は、していない**（認可ラボが必要）。
