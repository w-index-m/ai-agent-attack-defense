# 本リポジトリの検証方針 ── 主張から事実への4つのゲート

X(旧Twitter)で見た、LLMを使ったバグハンティングのパイプライン設計(@0xor0ne経由、2026-11-08)を
きっかけに、本リポジトリがこれまで実際にやってきた検証の積み重ねを、同じ「ゲート」の言葉で
整理しなおしたもの。**新しい方針を作ったわけではなく、既にバラバラのノートファイルに書いて
きたことを、1つの体系として言語化しただけ。**

## 元ネタの設計

ツイートで紹介されていたパイプラインは、LLMエージェントが見つけた脆弱性の「主張」を、
4段階のゲートに通す:

1. **Gate 0**: PoCが存在し、コンパイルできるか
2. **Gate 1**: クリーンなVMスナップショットで、PoCが実際にクラッシュを再現するか
3. **Gate 2**: そのクラッシュが本当に悪用可能か(nullデリファレンスやgraceful exitではない)
4. **Gate 3**: 一般ユーザー権限で発火するか(SYSTEM/adminの特権無しで)

すべて通過したものだけが`Validated Finding`として昇格し、途中で落ちたものは
**削除されず、`hallucinations/`というフォルダに残る**。

## 本リポジトリでの対応(ゲートの言葉で読み直す)

| ゲート | 本リポジトリでの実例 |
|---|---|
| **Gate 0: 機械的に反応するか** | `auto_vuln_scanner.py`の決定的な`detect_*()`が反応するか。Sigma/Datadog/Elasticルールの条件に一致するか。frameのtaint解析が指摘を出すか |
| **Gate 1: 脆弱版/修正版のペアで検証したか** | `run_regression.py`で、脆弱版は必ず検出・修正版は必ず誤検知0件を確認(現在15クラス30パターン)。frameの`file_view_safe`・`fetch_url_safe`での誤検知も、**このペア検証をやったからこそ**見つかった(`frame-sast-trial-notes.md`) |
| **Gate 2: 実機・実データで再現したか** | R26(Linuxカーネルのクラッシュ検知)は実際のdmesgログ375行で確認。SQLiteの`sleep()`代替(再帰CTE)は実測で約1秒の遅延を確認。netcheckは実サーバーで検証。frameは同じ入力で2回実行し完全に同じ結果になることを確認(決定性) |
| **Gate 3: 一次情報で裏取りしたか** | `lineage.md`の出典管理。Cairnの実被害事例は「複数の二次情報源のみ、一次情報での裏取りは一部できていない」と明記。NISC文書・Project YATA-Shieldも同様に「一次情報は未取得」と明記 |

## 落ちたものの扱い(`hallucinations/`相当)

元ネタの設計は、落ちた主張を**別フォルダに移す**ことで区別している。本リポジトリでは
フォルダを分ける代わりに、**同じ場所に残したまま、何が間違っていたかを明記する**という
やり方を一貫して採ってきた:

- `nisc-2026-11-05-taiou-notes.ja.md`: 「RCE・SSRF用のスキャナが無い」という自分の誤りを、
  後から見つけて訂正記録として残した(削除も隠蔽もしていない)
- `ai-sast-trial-notes.md`: AIが本物の脆弱性を「誤検知」として打ち消した事例を、
  打ち消されたまま埋もれさせず、明示的に記録
- `frame-sast-trial-notes.md`: `hardcoded_secret`への誤分類(本来`sql_injection`であるべき
  箇所)を、「良い結果」として誇張せず、見出しに「誤分類」と明記
- `defense-detection-notes.md`のR20・R21等: 「探索的ヒューリスティック・未確証」という
  ラベルを、検知ルールの説明文そのものに埋め込んでいる(後から読む人が、裏取り済みの
  ルールと未確証のルールを区別できるように)

## 実例: AIの判定は「Gate 0未満」(local-ai-sast)

`ai-sast-trial-notes.md`で試験した[sohampatil99/local-ai-sast](https://github.com/sohampatil99/local-ai-sast)は、
この体系に当てはめると良い反面教師になる。

- **Gate 0の条件は「機械的に反応するか」だが、本来は裏に「同じ入力なら同じ結果になる」という
  前提がある**(Sigmaルールの条件一致、`detect_*()`の判定、frameのソルバー証明は、どれも決定的)。
  local-ai-sastの判定は**この前提を満たさない**: 3Bモデルで独立5回実行したところ、検出数が
  3〜6/11とばれ、**OSコマンドインジェクション・パストラバーサルという、本来Gate 1(ペア検証)まで
  到達できたはずの本物の脆弱性を、5回中2回「誤検知」として自分で打ち消した**。
- つまりlocal-ai-sastの「`true_positive`」という自己申告は、**Gate 0の代わりにはならない**。
  これをGate 0として扱うと、同じコードに対して実行のたびに合格・不合格が入れ替わるという、
  決定的なゲートではあり得ない状態になる。
- **本リポジトリの対応**: `ai-sast-review-checklist.ja.md`で、「AIの`false_positive`判定を
  無確認で握り潰さない」「複数回実行して割れたら安全側に倒す」という手順を定めた。これは
  実質的に、**AIの判定を「Gate 0未満」の生の主張として扱い、Gate 0(ルールベースの決定的な
  再確認)を別途必ず通すこと**を要求している。7Bモデルに大きくしても検出数自体は広がらなかった
  (ルールだけと同じ5/11)ことも踏まえると、「AIを足せばGate 0の精度が上がる」という期待は
  このリポジトリの実測では支持されなかった。
- **frameとの対比**: 同じ「AI的な判定」でも、frameの`--hunt-authz`(LLMエージェントに探索させ、
  各判定を解決/未解決で機械的に仕分ける設計)は、**LLMの出力をGate 0に直接させず、間に機械的な
  検証を挟む**という点で、local-ai-sastより一段階体系に沿っている(`frame-sast-trial-notes.md`)。
  ただしframe自身も、`hardcoded_secret`への誤分類(本来`sql_injection`であるべき箇所)という、
  パターンマッチ部分(`evidence: matched`、ソルバー非経由)での誤りは免れていない。

## 検知ルール(R1–R31)をゲートで棚卸しした結果(2026-11-08)

「今あるルールは、実際どのゲートまで届いているのか」を数えてみた(詳細は
[`detections/README.md`](detections/README.md)の表に「到達ゲート」列として追記済み)。

| 到達ゲート | 該当ルール | 件数 |
|---|---|---|
| **Gate 2**(実機・実データ、または合成データで再現) | R1・R2・R3・R4・R5・R6・R7・R8・R9・R10・R12・R13・R14・R15・R16・R17・R21・R22・R23・R24・R25・R26 | 22件 |
| **🚫 Gate 0・実装不能(構造的、意図的に断念)** | R11 | 1件 |
| **Gate 0止まり(未着手。実装自体は可能)** | R18・R19・R20・R27–R31 | 8件 |

**追記(2026-11-08、続き)**: 「Gate 0のR1-R12で、実機検証できそうなものはあるか」という問いを
きっかけに、まずR1・R3・R4・R9・R10・R12の6ルールを、新規/拡張したスクリプトで合成ログ検証し、
Gate 2に引き上げた。続けて「gate0残り」の指示で、残っていたR2・R5・R6・R7・R8にも対応する
スクリプトを新規作成し(`container_privilege_check.py`・`file_event_check.py`・
`process_tool_check.py`)、同様に合成ログで検証した。**これでR1–R12のうち、Gate 0のまま残って
いるのはR11のみ**。R11は「汎用的なネットワークシグネチャが存在せず、アプリ側の計装が前提」と
ルール自体に明記されており、構造的に実機検証できない(アプリ固有の計装が無い限り、汎用スクリプト
では原理的に検証できない)。

31件中9件(約3割)がGate 0止まり。ただしこの9件は、性質が異なる2種類に分けて扱う:

1. **R11(実装不能・意図的に断念、1件)**: 上記の通り、原理的にスクリプト化できない。
   「できないものはできない」と正直にフラグを立て、これ以上の実装は追わない方針とした
   (2026-11-08、会話での確認済み)。
2. **R18・R19・R20・R27–R31(未着手だが実装自体は可能、8件)**: CVE/実被害事例から後付けで
   作った、比較的新しいルール。二次情報(報道・事後解析)からの推測で設計しており、
   **作った本人が「未確証」と明記したまま**。ただしR11とは違い、**ログを読んで判定する
   スクリプト自体は作れる**(調査済み、2026-11-08):
   - R18・R19は`status: stable`(確定済みの脆弱性パターン)で、Webアクセスログの単純な
     URI一致。R3(`web_recon_burst_check.py`)と同じログ形式で、実装は容易。
   - R20・R27・R28・R29・R30・R31は`status: experimental`で、ルール自体に「二次情報源
     からの推測で、確認済みのシグネチャではない」と明記されている。スクリプト化して
     Gate 2にしても、**この「未確証のヒューリスティック」という限界は残り続ける**
     (実装の有無とは別の軸の限界)。R31は`proxy_egress_check.py`にドメインリストを
     1つ追加するだけで実装できる、最も簡単なケース。
   - この8件への着手は、R11とは別に判断する(本書の集計はR11を除外して評価してよい)。

Gate 2まで届いている22件は、2つのグループに分かれる:

1. **バージョンチェック系**(R13・R14・R15・R16・R17・R21・R22・R23・R24・R25・R26): 各
   `scripts/*_check.py`が対応するCVEの影響範囲と、実際に動いているバージョンを突き合わせるだけの
   確認。**クラッシュそのものを検知する部分(ログ上の挙動パターン)は、この中にも未確証のまま
   残っているものがある**(R24・R25・R26の「クラッシュ検知」サブルール)。
2. **ログ読み取り系**(R1・R2・R3・R4・R5・R6・R7・R8・R9・R10・R12、2026-11-08追加):
   `proxy_egress_check.py`・`web_recon_burst_check.py`・`dns_water_torture_check.py`・
   `container_privilege_check.py`・`file_event_check.py`・`process_tool_check.py`が、合成の
   フォワードプロキシログ/Webアクセスログ/DNSクエリログ/コンテナイベントログ/ファイル書き込み
   ログ/プロセス実行ログを読み、Sigmaルールの条件(ドメイン一致・パス一致・閾値・順序相関)を
   そのまま実装して判定。**こちらも全て合成データのみでの検証**(本物のログフォーマットでの
   裏取りは未実施、各notesファイルに明記)。

**追記(2026-11-08)**: R23(F5 BIG-IP APM、`f5_bigip_apm_check.py`)は、当初`--version`モードしか
実機確認していなかったため「Gate 1相当」としていたが、残る3経路(`--apm-log`の閾値分岐・
`--core-dir`・`--tmm-finish`)を合成データで検証し、Gate 2に引き上げた。**ただし本物のBIG-IP実機・
本物のapmログフォーマットに対しては未検証のまま**(`f5-bigip-apm-check-notes.md`参照)。
「合成データでの検証」は、R26(実際のdmesgと合成ログの両方)より一段弱い、**全て合成データのみ**の
Gate 2であることは正直に書いておく。R1–R10・R12も同様に、全て合成データのみのGate 2である。

## 元ネタとの違い

- **強制力**: 元ネタはフォルダ構造という**仕組み**でゲートを強制する。本リポジトリは
  各ノートファイルに**人間が書く**ことで同じ効果を狙っており、強制力は弱い
  (書き忘れる・訂正し忘れるリスクが残る)。
- **検証の自動化**: `run_regression.py`・`tools/check_consistency.py`は自動化された
  ゲートだが、「一次情報の裏取り」(Gate 3相当)は自動化できておらず、毎回人間(このセッション)
  が意識して書くしかない。

## まとめ

この文書自体は新しいルールを作るものではなく、**既にやってきたことの棚卸し**。
今後、新しい文書やツールを追加する際は、ここで整理した4段階(機械的反応→ペア検証→
実機再現→一次情報裏取り)のうち、**どこまで通したか**を明記する、という書き方を意識する。
