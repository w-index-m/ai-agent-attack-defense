# モックLLMの使い道: 「ツール自体のバグ探し」の手法化

これまでの検証([`strix-local-backend-notes.md`](strix-local-backend-notes.md) 検証7、
[`cai-local-backend-notes.md`](cai-local-backend-notes.md) 検証2)で、台本によるモックLLMが
**対象アプリの脆弱性確認の配線テスト**だけでなく、**AIセキュリティツール自身の実装バグ**を
2件偶然見つける副産物になった。このページは、その2件を再現可能な一般的手法として整理し、
他のツールにも同じやり方で横展開できるかを検討する。

> 本ページは防御・検知の観点に限定。見つけた挙動を悪用する手順や、他者のツールへの
> 攻撃を目的としたものではない。対象は常に自分で立てたローカルの使い捨て環境。

## なぜモックLLMでバグ探しができるのか

モックLLMは「次に何をするか」を台本で固定して返すだけなので、**「LLM自身の判断が
賢いかどうか」という変数を排除**できる。これにより、エージェントフレームワーク側の
「配線」部分——会話履歴の組み立て、ツール呼び出しの実行、セッション状態の保存、
安全機構(ガードレール)の適用範囲——を、**決定的(deterministic)かつ無料・無制限に
繰り返して観察**できる。実LLMで同じことをしようとすると、推論のゆらぎがノイズになって
「フレームワーク側のバグ」なのか「LLMの気まぐれ」なのか切り分けが難しい。

## 手法: 境界ケースを台本に書き、生ログを突き合わせる

2件の発見に共通するやり方を一般化すると、次の4ステップになる。

1. **「素直な単発シナリオ」ではなく「境界ケース」を台本にする**。単発の脆弱性確認
   (ターン2でcurl、ターン3でレポート提出)は配線の疎通確認にしかならない。バグを
   見つけたいなら、以下のような**フレームワークの設計上の前提を突く**シナリオを書く:
   - 複数ステップを繋いだ**攻撃チェーン**(1手目の結果を2手目以降が参照する前提のある
     シナリオ)
   - **マルチエージェントのハンドオフ**(エージェントAからエージェントBに制御が移る境界)
   - ツール出力の中に、**ユーザー入力っぽく見える/指示っぽく見える文字列**を混ぜる
     (間接プロンプトインジェクションの形を模する)
2. **最終成果物(レポート)だけでなく、生のやり取りを突き合わせる**。フレームワークが
   自分で「完了」と報告した内容を鵜呑みにせず、以下を直接確認する:
   - モックLLMサーバーが受け取った**生リクエストのログ**(本リポジトリでは
     `/tmp/mock_llm/requests.jsonl`のような形で実装)
   - フレームワーク自身のセッション状態ファイル(Strixなら`.state/agents.db`)
   - 「次のターンへのリクエストに、前のターンの結果が本当に含まれているか」を
     メッセージ配列レベルで数える
3. **フレームワークの内部関数を、エージェントループを経由せず直接呼ぶ**。CAIの例では、
   `detect_injection_patterns()`という検知関数を、エージェントを起動せずPythonから
   直接importして呼び出し、入力の「形」(素のテキスト vs `{'role': 'tool', ...}`)を
   変えるだけで挙動がどう変わるかを比較した。エンドツーエンドでの再現より、
   関数単体の境界値テストの方が原因特定が速い場合がある。
4. **クリーンな状態から2回以上再現する**。1回だけの観測は環境由来のたまたまかもしれない。
   本リポジトリのStrix検証では、新規の対象アプリ・新規のモックサーバー・新規の
   `strix_runs`ディレクトリで2回独立に再現し、同じ挙動(1手目の結果の欠落)を確認した。

## 事例1: Strix — 1手目のツール実行結果が後続の会話履歴から消える

- **台本**: SSRF(`/fetch_url`で内部限定サービスの秘密を取得)→IDORログイン→IDORピボット→
  `create_vulnerability_report`→`finish_scan`、という5手の攻撃チェーン。
- **発見**: SSRFのコマンド自体は対象アプリの実アクセスログに200で記録されており
  **実際に実行されている**。しかし、3手目以降モックLLMへ送られるリクエストの
  `messages`配列には、**SSRFの結果が一度も含まれていなかった**(システムプロンプト+
  初期入力のみの2メッセージから始まり、IDORログイン以降の結果しか積み上がらない)。
  2回の独立した再現で同じ結果。
- **意味**: 「実LLMが自分の過去の行動を踏まえて次を判断する」という前提の実運用では、
  1手目の観測結果が欠落したまま2手目以降の判断が進みうる、という潜在的な問題。
  原因(Strix本体のバグか`local`バックエンド固有の実装詳細か)の特定はスコープ外。
  詳細: [`strix-local-backend-notes.md`](strix-local-backend-notes.md) 検証7。

## 事例2: CAI — プロンプトインジェクション検知がツール出力を素通りする

- **手法**: 台本ではなく、CAIのガードレール関数`detect_injection_patterns()`を
  直接importして呼び出し、同じ悪意ある文字列を「素のユーザー入力」と
  「`{'role': 'tool', ...}`形式のツール出力」の2通りで渡して比較。
- **発見**: (1) `CAI_GUARDRAILS`環境変数が既定で`false`のため、検知機構自体が
  既定では完全に無効。(2) 明示的に有効化しても、`detect_injection_patterns()`自身が
  `if "'role': 'tool'" in text: return False, []`という早期リターンを持っており、
  ツール出力の形をした文字列は**検知対象から除外**される(素のユーザー入力なら
  5パターンにヒットする同一文字列が、ツール出力形式だと0ヒット)。さらに
  `@input_guardrail`はSDK設計上セッション開始時の1回しか評価されない。
- **意味**: 「素の自己申告的な指示上書き」には機能するが、エージェント型ツールにとって
  最も現実的な脅威である**ツール出力経由の間接プロンプトインジェクション
  (OWASP LLM01)**には、既定でも有効化後でも届いていない。CAI固有の実装詳細の指摘で
  あり、LLM一般の脆弱性ではない。詳細: [`cai-local-backend-notes.md`](cai-local-backend-notes.md) 検証2。

## 事例3: hackingBuddyGPT — `api_base`設定項目が丸ごとデッドコード

- **手法**: 台本を書く前に、まず手法のステップ3(内部関数を直接呼ぶ)の前段として
  「ソースを直接読む」を実施したところ、境界ケースを試すまでもなくコード中に
  発見があった。
- **発見**: LLM接続先を切り替える設定フィールド`api_base`が、実際に
  `litellm.completion()`へ渡す呼び出し箇所で`# api_base=self.api_base, TODO: why
  is this not working anymore`とコメントアウトされていた。全コードベースを検索しても
  他に使用箇所は無く、**ユーザーが`api_base`を設定しても完全に無視される**(エラーも
  出ない)。実機で`api_base`にモックサーバーを指定して呼び出したところ、モックには
  一切届かず、litellmの既定(実際のOpenAI API)への接続を試みて失敗することを確認した。
- **回避策の確認**: litellm自身が読む`OPENAI_API_BASE`環境変数を設定したところ、
  hackingBuddyGPT側の壊れた設定をバイパスしてモックサーバーに正しく到達することを
  確認した。
- **意味**: 開発者自身がTODOコメントで認識している既知の不具合で、悪意ある入力とは
  無関係の、素朴な「設定が効かない」バグ。StrixやCAIの発見より地味だが、
  「ソースを読むだけで見つかる」という、手法のステップ1(境界ケースの台本)より
  手前の段階でも価値があることを示した。詳細:
  [`hackingbuddygpt-local-backend-notes.md`](hackingbuddygpt-local-backend-notes.md) 検証1。

## 横展開できそうな対象

同じ4ステップの手法を、まだ試していない独立したAIセキュリティ/エージェントツールに
適用できないか、という観点での候補(いずれも未着手、優先度順ではない):

- **PentestGPT**: 着手した。`pentestgpt_legacy`(対話型、OpenAI互換APIのモック化が
  素直に効いた)ではこの境界ケースでバグは見つからず、新しい`pentestgpt_agent`
  (Claude Code/Codexを駆動する自律型、LLM API直叩きではないため同じ手法が
  そのままは通用しない)は未着手のまま残っている。詳細:
  [`pentestgpt-local-backend-notes.md`](pentestgpt-local-backend-notes.md)。
- **hackingBuddyGPT**: 着手した。`api_base`設定項目が丸ごとデッドコードだった
  (下記「事例3」参照)。`OPENAI_API_BASE`環境変数で回避できることも確認。詳細:
  [`hackingbuddygpt-local-backend-notes.md`](hackingbuddygpt-local-backend-notes.md)。
- **Cairn**(本リポジトリの`cairn-lab/`で既にモックdispatcher配線は確認済み、PR #71):
  マルチエージェント構成のワーカー間で、Strixと同種の「前の手の結果が欠落する」問題が
  無いかを、攻撃チェーン型の台本で再検証する余地がある。
- 他のフレームワークでも、**ツール出力経由の間接プロンプトインジェクション**への
  ガードレール適用範囲(CAIで見つかったのと同じクラスの穴)を、関数直接呼び出しで
  横断チェックする。

## 限界(正直に)

- この手法で見つかるのは**フレームワークの配線・実装のバグ**であり、「実LLMが賢く
  脆弱性を発見できるか」という本来の価値は一切検証できない(モックLLMは台本どおりにしか
  動かないため)。
- 見つかった2件とも、**原因の根本特定(なぜそうなるか)までは踏み込んでいない**
  (再現性の確認と挙動の記述まで)。対象がOSSであっても、Issue報告や修正PRは
  本リポジトリのスコープ外。
- 「境界ケースを突けば必ずバグが出る」わけではなく、これまで2回試して2回とも
  何かしら見つかった、という経験則の域を出ない。

> 確認・検知の設計に限定。攻撃の実行手順や安全機構の回避方法は含めない。
