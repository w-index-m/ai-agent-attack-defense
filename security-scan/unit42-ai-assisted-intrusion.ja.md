# Unit 42「AI支援サイバー攻撃」事例の分析（一次情報）

English: [`unit42-ai-assisted-intrusion.en.md`](unit42-ai-assisted-intrusion.en.md)

Palo Alto Networks Unit 42 が公開した実インシデント報告
**"An AI-Assisted Cyber Attack: Inside a Unit 42 Investigation"**（2026-09-02 公開、2026-09-03/09-04 訂正）の分析。
本リポジトリがこれまで扱ってきた Strix/Cairn/Hermes/ARTEX は「AI エージェントというツール自体」の防御解析だったが、
本件は**実際にそのようなツールが悪用された、実世界のインシデント**の一次報告である点で異なる。

> 方針は同じ：**検知・防御の設計に限定**。攻撃の実行手順・兵器化・安全機構の回避方法は含めない。
> 本書は Unit 42 の公開記事の内容を転記・整理したものであり、独自の追加調査は行っていない。

## 1. 概要

- 人間の攻撃者が、**frontier AI モデル＋攻撃特化型 agentic フレームワーク**を用いて、企業ネットワークへの侵入を自動化したと交渉の場で自認した。
- 通常は複数のレッドチームが**約2週間**かけるような規模の作業を、**10時間未満**で完了。
- 攻撃者はエージェントに侵入の全工程を任せ、**人間は目標設定と重要な意思決定のみ**を行った（Unit 42 の図1が示す構造）。
- 攻撃終了後、エージェントに被害組織の**セキュリティ監査レポート（80ページ、具体的な脆弱性多数を記載）**を作成させ、置き土産として残した。

## 2. 10時間の侵入チェーン

| 段階 | 内容 |
|---|---|
| ① 侵入・マッピング | 公開Webサービスの脆弱性を突いてネットワークへトンネル。自動化された偵察エージェントが内部マイクロサービスをマッピング |
| ② シークレット収集 | サブエージェントが社内のコードリポジトリを横断的に探索し、ハードコードされたトークン・サービスパスワードを抽出 |
| ③ 権限奪取 | 窃取したトークンでシークレット管理システムに侵入し、root相当の管理者認証情報を獲得 |
| ④ パイプライン悪用 | カスタムワークフローで CI/CD を乗っ取り、クラウドアクセスキーを持ち出し。Terraform 設定へのバックドア設置も試みたが、**強固なブランチ保護により阻止された** |
| ⑤ AI基盤の乗っ取り | 窃取したクラウドキーで、被害組織自身の AI エンドポイントを**事後の攻撃インフラとして転用**（計算資源・通信の隠れ蓑として悪用） |

## 3. AIの関与を示した痕跡（Unit 42 が明記）

- 複数の frontier AI モデルへの**並列 LLM 呼び出し**
- エージェント間・セッション間で情報を受け渡す**構造化 Markdown ファイル**
- UI 要素の残骸があることから「AI 生成と高い確度で評価された」**カスタムスクリプト**

Unit 42 はこの3点を「防御側が agentic 攻撃を見分ける際の痕跡」として明示的に挙げている。

## 4. MITRE ATT&CK × MITRE ATLAS 対応（Unit 42 公開の表をそのまま転記）

| 侵入段階 | 攻撃者の行動 | MITRE ATT&CK | MITRE ATLAS（AI特有） |
|---|---|---|---|
| 初期侵入・偵察 | 公開Webサービス侵害／自動サービス発見ツールによる偵察 | T1190（Exploit Public-Facing Application）、T1046（Network Service Discovery） | AML.T0000（Initial Access）、AML.T0002（AI-Automated Reconnaissance） |
| 認証情報アクセス | コードリポジトリ横断でのシークレット探索 | T1552.001（Credentials In Files） | AML.T0014（Credentials Harvesting） |
| 権限昇格 | シークレット管理システム侵入による管理者権限奪取 | T1555（Credentials from Password Stores） | AML.T0016（Privilege Escalation via Automated Pivot） |
| パイプライン悪用 | CI/CD操作の実行、IaCツールの改ざん試行 | T1578（Modify Cloud Compute Infrastructure） | AML.T0010（ML/DevOps Pipeline Interception） |
| AI基盤の悪用 | 窃取したキーでクラウドAIモデルを呼び出し | T1078（Valid Accounts） | AML.T0043（LLM Invocations via Stolen API Keys） |

## 5. Unit 42 が挙げた教訓（防御側向け）

- **エージェントは攻撃フローの各ステップ間の時間を圧縮する**：生のツール出力を解釈し、即座に次の一手を決める設計のため、全体の速度が上がる。
- **エージェントは識別可能な痕跡を残す**：構造化Markdown、Pythonのキャッシュファイル、対になったアセットフォルダなど。
- **冗長な永続化を並行して確立できる**：SSH鍵・サーバーレス関数・コンテナ再起動ポリシー・クラウドID・CI/CDパイプラインに同時多発的に仕込める。
- **組織自身のAI基盤を事後インフラとして悪用できる**：正規のトラフィックに紛れさせ、コストも被害者側に転嫁できる。

Unit 42 が推奨する対策（記事の要約）：
- 認証情報の失効・OAuthセッション終了・CI/CD凍結・クラウドアカウント隔離を**同時に実行する自動化プレイブック**
- モデルエンドポイント・APIキー・MCPゲートウェイ・AIツール連携を**インフラとして一元管理・棚卸し**し、最小権限＋レート制限＋診断ログを適用
- バースト的なAPI要求・急激な401/200の切り替わり・並列認証・想定外アイデンティティからの突然のモデル利用といった**挙動ループの検知**
- IaCリポジトリへの**必須の複数人レビュー＋イミュータブルなブランチ保護**

## 6. 本リポジトリの R1–R8 / G1–G6 との対応

| Unit 42 事例の要素 | 観測点 | 本リポの検知 |
|---|---|---|
| コードリポジトリ横断でのシークレット探索（サブエージェントによる） | 1プロセス配下での多数ファイル/リポジトリへの短時間アクセス | **R7**（偵察的ツール連続実行と同じ発想） |
| CI/CDパイプライン乗っ取り・クラウドキー持ち出し | 永続化・権限拡大の新規作成 | **R5**（新規ジョブ/認証情報の作成）・**G5**（ツール権限拡大の要求） |
| 窃取したクラウドキーでの自社AI基盤呼び出し | サーバ/パイプライン系ホストからのLLM API egress | **R1/R4**（まさに本リポのR1が最優先に置く検知対象そのもの） |
| Terraformへのバックドア試行がブランチ保護で阻止 | 正規運用時の統制 | **G5/G6 相当の防御が機能した実例**（本リポがARTEX分析で触れた「内蔵ガバナンス」の重要性を裏付け） |
| 構造化Markdownでのエージェント間情報受け渡し | エージェント特有の痕跡 | 既存のR1–R8には無い**新しい着眼点**。ファイル共有パターンの監視は今後の検討課題（§7） |
