# process_tool_check: プロセス実行ログからR6・R7・R8(起動側)を確認するツール

## 経緯

`verification-gates.md`の棚卸しで見つかったギャップ。R6(相関、`r6_correlation_eql.json`の
代表例)・R7(`r7_rapid_multitool_execution.yml`)・R8起動側(`r8_webshell_placement_and_spawn.yml`
の後半)は、どれも「プロセス実行イベント」という同じログ源が前提の**ルール定義**で、投入先は
SIEM側が前提。`scripts/process_tool_check.py`は、この3つを同じプロセス実行ログに対して直接
実行する版。

## やること(確認専用、読み取りのみ)

- プロセス実行イベントのログ(JSON Lines)を読む。
- **R7**: 同一の親プロセスIDの下で、既知のセキュリティツール(`nmap`・`ffuf`・`sqlmap`等)が
  5種類超(閾値はSigmaルールの`> 4`と同じ)実行されたパターンを検知。
- **R6**: 同一の親プロセスIDの下で、`nmap`実行のあと、別の攻撃ツールが実行された(順序付きの
  相関)パターンを検知(ElasticのEQLサンプルと同じ発想)。
- **R8(起動側)**: Webサーバー/アプリケーションサーバーのプロセス(`java`・`nginx`・`httpd`・
  `apache2`・`php-fpm`等)がシェル(`sh`・`bash`・`dash`・`zsh`)を起動したパターンを検知。
- プロセスの起動・停止は一切しない。

## 使い方

```bash
python3 scripts/process_tool_check.py --log-path process_events.jsonl
```

終了コード: 0(ヒット無し) / 1(ヒット有り) / 2(ログ読み取り失敗)。

## 確認したこと(2026-11-08、このサンドボックス内)

- 合成ログで、R7(同一親の下で5種類のツール実行)・R6(nmap→ffufの順序付き相関、2通りの親で
  確認)・R8起動側(apache2がbashを起動)を正しく検出。
- 陰性対照: 3種類のみのツール実行(閾値未満、R7は不検知。ただしR6は閾値と無関係な独立の
  シグナルのため、同じログでnmap→ffufの順序があれば別途検知する。これは意図した挙動)、
  Webサーバーでないプロセス(`make`)がシェル(`sh`)を起動するケース(R8は不検知)を確認。

## 確認していないこと

- 実際のauditd/Sysmon等が出力する**本物の**プロセス実行ログでの動作(今回はすべて合成ログ
  での検証)。
- R7の時間窓(5分)は、タイムスタンプが連続したログでは厳密なスライディングウィンドウでは
  なく、同一親プロセスの全イベントを1つの集合として数える簡略化をしている(見逃しより
  誤検知寄りに倒す設計。本物のログでの精度検証は未実施)。

## 2026-11-08追記: R6・R7をGate 3に区分(`verification-gates.md`棚卸しとの整合)

R6・R7は、Gambit Securityが自社で発見・回収した攻撃者ステージングサーバーに基づく一次報告
(2026-09-22)を出典としており、Gambit自身の一次情報源にあたる。直接fetchはブロックされて
いるため、複数の独立した二次情報源の一致した報告で確認した。これにより両方をGate 3に区分
した。検知ロジック自体(閾値・集合カウント)は本リポジトリ独自の構成のままである。
